# 실행 계약과 전략 규칙

이 문서는 현재 NTIS Domain RAG 저장소의 **실행 계약**을 정리합니다.

이 문서 하나만 읽어도 아래를 이해할 수 있도록 구성했습니다.

- SEARCH / LOOKUP / JOIN의 의미
- planner stage별 책임
- `ids_map` / `candidate_keys` 규칙
- `join_key_mode`
- `project_key_policy`
- no-result 정책
- `pjt_id` / `pjt_no` 환경 계약

## 1. 핵심 기준선

- 시스템 형태: retrieval-first + chat UX
- 실행 기준: staged-only + strict
- planner invalid / contract violation: fail-close
- lower-layer fallback strategy: 기본 경로에서 금지
- `IntentPayloadV3`: 활성 transport 계약
- `strategy_version="v3"`: 활성 의미 계약

## 2. SEARCH / LOOKUP / JOIN

### SEARCH
의미:
- 넓은 주제 탐색
- recall과 ranking이 중요

언제 쓰나:
- broad topic query
- explicit id가 없음
- 강한 lookup signal이 없음
- relation이 없음

주의:
- SEARCH는 lookup-style hard must filter를 과하게 걸지 않는다.

### LOOKUP
의미:
- 정확 조회
- identifier 또는 강한 제약 기반 조회

언제 쓰나:
- explicit id
- `candidate_keys.project_key` 또는 `candidate_keys.perf_key`
- 사람/기관 이름 기반 조회
- `action in (list, detail, stats, download)`

주의:
- 사람/기관 질의는 기본적으로 LOOKUP 우선이다.
- `과제번호`는 즉시 resolved `pjt_id` 또는 `pjt_no`로 확정하지 않는다.

### JOIN
의미:
- 관계형 multi-hop retrieval

언제 쓰나:
- project ↔ perf 관계가 분명함
- relation과 join seed가 함께 있음
- `perf_to_project_to_perf`, `multi_hop_bundle` 같은 query-graph가 명확함

주의:
- JOIN은 strict resolved-key mode와 deferred discovery mode를 구분해야 한다.

### `project_key_policy`
지원 값:
- `resolved_pjt_id`
- `resolved_pjt_no`
- `ambiguous_or`

의미:
- `ambiguous_or`는 exact OR exact discovery를 뜻한다.
- free-text fallback을 뜻하지 않는다.

### `join_resolution_policy`
지원 값:
- `auto_resolve`
- `dual_branch`

의미:
- deferred join에서 runtime이 key kind를 어떻게 확정할지 정한다.

## 5. `join_key_mode`

### `instance`
- resolved `pjt_id` 기반 실행
- strict resolved-key mode

### `group`
- resolved `pjt_no` 기반 실행
- strict resolved-key mode

### `deferred`
- ambiguous exact project key 기반 실행
- `candidate_keys.project_key`와 `project_key_policy=ambiguous_or`가 함께 있어야 한다.
- hop1 discovery 뒤 runtime이 `instance`, `group`, `dual_branch` 중 하나를 결정한다.

중요:
- `resolved_runtime_join_mode`는 planner 필드가 아니라 runtime 산출물이다.
- `dual_branch_used`는 runtime observability 필드다.

## 6. relation / head 규칙

대표 relation:
- `project_perf`
- `perf_project`
- `perf_to_project_to_perf`
- `multi_hop_bundle`

기본 head 규칙:
- `project_perf`이면 `head=perf`
- `perf_project`이면 `head=project`

원칙:
- `mode=join`에서는 relation target과 head가 맞아야 한다.

## 7. no-result와 strict failure

### 일반 no-result
아래는 정상적인 빈 결과다.

- `lookup` + `reason=no_reranked`
- `join` + `reason=no_reranked`
- deferred hop1 0-hit
- dual-branch 0-hit

결과:
- `normal_no_result`

### strict failure
아래는 계약 위반이다.

- resolved `instance/group`인데 필요한 seed가 없음
- invalid enum
- unsupported relation
- malformed payload
- resolved identifier semantics conflict

결과:
- `StrategyViolation` 또는 strict contract failure

## 8. `pjt_id` / `pjt_no` 환경 계약

환경 기준:
- `RAG_KEY_PJT_ID=pjt_id`
- `RAG_KEY_PJT_NO=pjt_no`

원칙:
- `pjt_id`는 instance key다.
- `pjt_no`는 group key다.
- 둘을 같은 payload field처럼 해석하면 안 된다.
- startup 시 둘이 collapse되면 fail-fast 해야 한다.

주의:
- group join resolution이 `pjt_no -> pjt_id`로 확장될 수는 있다.
- 하지만 이 확장이 원래 의미 구분을 지우지는 않는다.

## 9. 확장 runtime 규칙

### comparison
- aggregation payload를 answer generation 전에 만든다.
- 대표 metric:
  - `paper_count`
  - `patent_count`
  - `report_count`
  - `perf_total_count`

### series
- `output_type=series`는 실제 runtime evidence를 만든다.
- `pjt_no` 기반 series는 group/instance 의미를 섞으면 안 된다.

### reverse trace
- `perf -> project -> perf` 흐름은 runtime payload와 로그에 relation chain을 남겨야 한다.
- hop3 empty는 partial success다.

### anchor resolution
- researcher/org anchor는 planner-first로 정규화한다.
- role-specific org execution은 resolved role truth가 있어야 한다.
- seedless `JOIN(instance)` + unresolved researcher/org pairing은 strict join을 강제하지 않고 downgrade한다.

### pattern analysis
- `pattern_kind`는 planner-first metadata다.
- runtime은 지원되는 kind에 대해서만 계산한다.
- answer layer가 raw payload에서 임의 패턴 결론을 만들면 안 된다.

### multi-hop bundle
- researcher/org -> project -> multiple downstream targets를 하나의 payload로 다룬다.
- ambiguity는 strict JOIN 강제가 아니라 downgrade + guidance로 처리한다.

## 10. 한 줄 요약

현재 계약의 핵심은 이렇습니다.

- planner가 retrieval intent를 고정한다.
- runtime은 그 intent를 검증하고 실행한다.
- `deferred`는 실패가 아니라 합법 전략이다.
- `pjt_id`와 `pjt_no`는 절대 섞지 않는다.
- 빈 결과와 계약 위반을 같은 것으로 취급하지 않는다.
