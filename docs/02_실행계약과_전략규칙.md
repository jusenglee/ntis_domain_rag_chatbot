## 7. View State 계약

- 세션 메모리에는 `last_canonical_evidence`, `last_render_profile`와 별도로 `view_state`를 저장한다.
- `view_state`는 아래 4개를 포함한다.
  - `latest_display_snapshot`
  - `latest_focus_entity`
  - `detail_cache`
  - `raw_candidates_cache`
- `raw_candidates_cache`는 디버그/추적용이며 후속 질의 anchor의 source of truth로 사용하지 않는다.
- `latest_display_snapshot`은 서버가 실제로 사용자에게 보여준 visible item 순서를 보존한다.

## 8. Display-first follow-up 규칙

- `n번째`, `첫 번째`, `두 번째` 해석은 항상 `latest_display_snapshot.items[display_rank]` 기준으로만 수행한다.
- `그 과제`, `이 과제`, `해당 과제`는 우선 `latest_focus_entity`로 해석한다.
- 명시적 `pjt_id`/`pjt_no`가 있으면 snapshot/focus보다 우선한다.
- `view_state`가 없는 경우에만 기존 `canonical_evidence`/`prev_context` follow-up resolver를 호환 경로로 사용한다.

## 9. display_limit 계약

- `QuestionAnalysisV3.limit`는 retrieval budget이다.
- `QuestionAnalysisV3.display_limit`는 실제 사용자에게 보여줄 visible item 수다.
- `display_limit <= limit`를 강제한다.
- list/relation/comparison/series/stats 응답은 서버가 먼저 visible subset을 확정하고 snapshot을 저장한 뒤 그 subset만 후속 answer generation에 넘긴다.

## 10. Detail coverage 계약

- detail 응답은 서버가 `DetailCoverage`를 계산한다.
- `detail_level`은 `not_found`, `profile_only`, `rich_detail`만 허용한다.
- `profile_only`면 기본 프로필을 우선 응답하고, 부족한 rich detail만 부족하다고 알린다.
- 동일 entity 후속 detail 질의는 `detail_cache`를 우선 조회한다.
