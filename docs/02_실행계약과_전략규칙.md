# 실행 계약과 전략 규칙

이 문서는 planner, retrieval, answer generation 사이의 현행 계약을 정리한다.

## 1. 기본 계약
- `SEARCH`, `LOOKUP`, `JOIN` 의미를 서로 바꾸지 않는다.
- source of truth는 `normalized_intent.ids_map`과 `QuestionAnalysisV3`다.
- `strategy_meta`는 실행 보조 metadata이며 식별자 truth를 대체하지 않는다.
- `pjt_id`는 instance key, `pjt_no`는 group key다. 두 값을 같은 의미로 섭지 않는다.

## 2. Follow-up 해석
- `Reference Context`와 `latest_display_snapshot`을 기준으로 ordinal 또는 deictic follow-up을 해석한다.
- `1번 과제`, `2번 과제`, `그 과제` 같은 표현은 deterministic resolver가 우선 처리한다.
- follow-up에서 선택된 seed는 `ids_map`에 주입하고 `strategy_meta`에는 근거와 source를 남긴다.

## 3. Planner 책임과 sanitization
- explicit count list 질의에서 `limit`과 `display_limit`를 정하는 책임은 planner에 있다.
- planner가 비정상 count를 내리면 서버 fallback이 보정하되, 결과는 `MAX_TOP_K_SIZE` 상한 안에 머물러야 한다.
- detail 질의는 planner-first 원칙을 유지하더라도 `limit=1`, `display_limit=1` 계약을 유지한다.
- ordinal noise가 filter에 섞여 들어오면 strip + warn을 적용하고 `PLANNER.FILTER.ORDINAL_STRIPPED` 로 기록한다.

## 4. display_limit 계약
- `QuestionAnalysisV3.limit`는 retrieval budget이며 runtime top-k의 단일 source of truth다.
- `QuestionAnalysisV3.display_limit`는 실제 사용자에게 보여줄 visible item 수다. retrieval top-k를 직접 결정하지는 않는다.
- `display_limit <= limit`를 강제한다.
- 사용자가 `N건`처럼 개수를 명시한 list 계열 질의는 planner가 `limit/display_limit`를 직접 정한다.
- planner 값이 없거나 비정상이면 서버 fallback이 개수를 보정하되 `MAX_TOP_K_SIZE` 상한을 넘지 않는다.

## 5. Display snapshot과 canonical evidence
- list/relation/comparison/series/stats 응답은 먼저 visible subset을 확정하고 `latest_display_snapshot`을 저장한다.
- snapshot에 들어가는 `documents`와 `canonical_evidence`는 같은 index cardinality를 공유해야 한다.
- `canonical_evidence`가 부족하면 서버가 docs를 기반으로 보강하고 `RAG.CANONICAL_EVIDENCE.DERIVED` 로 기록한다.
- 보강 후에도 길이가 엇갈리면 `RAG.DISPLAY_INPUT_MISMATCH`를 남기고 min cardinality로 정렬한다. count triage는 `RAG.COUNT_PIPELINE` 로그와 함께 본다.

## 6. no-result와 strict failure
- `lookup` 또는 `join` 계열에서 `no_reranked`가 발생하면 contract violation으로 처리할 수 있다.
- resolved seed가 있는데도 relation/join이 빈 결과를 내면 일반 free-text fallback으로 무단 전환하지 않는다.

## 7. Detail coverage 계약
- detail 응답은 `DetailCoverage`를 계산해 `not_found`, `profile_only`, `rich_detail` 수준을 판정한다.
- `profile_only`면 기본 프로필을 우선 응답하고, 필요한 rich detail만 부족하다고 안내한다.
