# 실행 계약과 전략 규칙

이 문서는 planner, retrieval, answer generation(답변 생성) 사이에서 지금 지켜야 하는 약속을 정리한다.

## 한 줄 요약
- 이 문서는 시스템이 중간 단계에서 멋대로 뜻을 바꾸지 않게 잡아두는 "절대 바꾸면 안 되는 실행 약속"의 기준 문서다.

## 이 문서를 읽을 사람
- 개발자, QA, 운영자
- PM이나 비개발자는 상단 요약과 용어 풀이만 먼저 읽으면 된다.

## 이 문서에서 바로 찾을 수 있는 것
- `SEARCH / LOOKUP / JOIN` 경계
- follow-up 해석 기준
- display snapshot / detail coverage / answer context 계약
- planner V2와 pre-planner scope resolution 약속

## 지금 챙길 것
- 실행 기준 진실원은 `normalized_intent.ids_map`과 `QuestionAnalysisV3`다.
- `pjt_id`와 `pjt_no`는 절대 같은 의미로 다루지 않는다.
- `answer_context_text`는 사용자/모델용, `debug_answer_context_text`는 로그/디버그용이라는 분리를 유지한다.
- 이 문서에서 절대 깨지면 안 되는 것은 "질문 뜻, 식별자, 실행 전략, 근거의 역할" 네 가지다.

## 핵심 용어 빠른 풀이
- `contract`: 단계 사이에서 절대 흐리면 안 되는 약속
- `canonical evidence`: raw 검색 결과를 LLM에 보여주기 전에 정리한 근거
- `follow-up`: 앞 턴의 대상을 이어받는 후속 질문
- `groundedness`: 답변이 실제 근거 안에 있는지 보는 판단
- `drift`: 질문 뜻이 검색 질의나 실행 중간에 흐트러지는 현상
- `baseline`: 최소한 반복해서 확인해야 하는 검증 묶음

## 1. 먼저 기억할 실행 약속
- `SEARCH`, `LOOKUP`, `JOIN` 의미를 서로 바꾸지 않는다.
- 기준 진실원(source of truth)은 `normalized_intent.ids_map`과 `QuestionAnalysisV3`다.
- `strategy_meta`는 실행을 돕는 보조 정보일 뿐, 식별자의 기준값을 대신하지 않는다.
- detail exact lookup과 detail cache fast-path의 기준 seed는 항상 현재 turn의 `normalized_intent.ids_map`이다.
- `strategy_meta.seed_map`은 진단과 보조 설명용 메타데이터일 뿐이며, active execution truth를 대체하지 않는다.
- `pjt_id`는 개별 과제 식별값이고, `pjt_no`는 같은 묶음의 과제를 가리키는 값이다. 두 값을 같은 뜻으로 다루지 않는다.

## 2. 후속 질문은 이렇게 해석한다(Follow-up)
- `Reference Context`와 `latest_display_snapshot`을 보고 사용자가 앞에서 말한 대상이 무엇인지 다시 잡는다.
- `1번 과제`, `2번 과제`, `그 과제` 같은 표현은 먼저 규칙 기반으로 분명하게 해석한다.
- follow-up에서 고른 기준값(seed)은 `ids_map`에 넣고, 왜 그렇게 골랐는지는 `strategy_meta`에 남긴다.
- `출처 N` follow-up은 display ordinal이 아니라 reference-context owner가 먼저 해석한다. resolve되면 `seed_source=reference_context_source_reference`, `followup_reference_kind=source_reference`, `anchor_reference_kind=source_reference`가 함께 남아야 한다.
- `출처 N` follow-up에서 reference-context owner가 `missing_context` 또는 `none`만 반환한 경우에만 display snapshot ordinal fallback을 허용한다. 이 fallback도 `followup_reference_kind=source_reference`와 `anchor_reference_kind=source_reference`를 유지해야 한다.
- resolved follow-up이 `perf` 또는 `project` 맥락에서 선택되면 `request_facade`는 context owner lock만 선언하고, `planner_service.apply_planner_strategy()`가 `base_route/target_cols`의 최종값을 그 맥락에 맞게 강제한다. retrieval 실행 단계는 이 기준을 다시 바꾸지 않는다.

## 3. planner는 여기까지만 책임진다(sanitization)
- 사용자가 `3건`처럼 개수를 분명히 말한 목록 질문에서는 planner가 `limit`과 `display_limit`를 정한다.
- planner가 이상한 개수를 주면 서버가 한 번 보정하지만, 결과는 `MAX_TOP_K_SIZE`를 넘으면 안 된다.
- `retrieval_query`는 planner가 만든 짧고 핵심만 남긴 질의를 우선 사용한다.
- resolved follow-up anchor가 있는 lookup/detail에서 planner query가 원래 대상을 놓치면, 서버는 그 대상을 다시 살린 compact query로 고친다.
- resolved project detail follow-up에서는 `1번`, `그 과제` 같은 말을 성과 축으로 잘못 돌리지 않으며, retrieval은 원래의 project anchor를 유지한다.
- 기존 `prev_context`가 남아 있어도 사용자가 이전 문맥보다 더 새롭거나 갱신된 사실을 다시 확인하려는 의미라면, knowledge sufficiency LLM은 `requires_new_knowledge=high`, `prefer_fresh_retrieval=true`로 판단해야 한다.
- cache-backed detail turn 직후처럼 `prev_context`가 비어 있어도 active anchor seed와 explicit follow-up 맥락이 살아 있으면, knowledge sufficiency는 이 freshness probe를 생략하면 안 된다. `detail`이 search-required action이어도 LLM freshness 판단은 먼저 실행하고, retrieval 단계는 그 결과만 소비한다.
- `prefer_fresh_retrieval=true`인 anchored detail follow-up은 stale detail cache나 anchor-only exact lookup(`top_k=1`)에 갇히지 않고, 현재 질문을 기준으로 다시 검색하되 anchor seed는 query 안에 보존한다.
- 이 복구는 임시 편법이 아니라 원래 계약을 다시 맞추는 동작이다.
- planner 힌트 때문에 질문 뜻이 바뀌거나 식별자/연도 정보가 빠지면, 원래 질문으로 되돌아가는 fallback을 계속 쓸 수 있다.
- detail 질문은 planner를 먼저 따르더라도 `limit=1`, `display_limit=1` 규칙을 지켜야 한다.
- `1번째`, `그`, `이번` 같은 말이 filter에 섞여 들어오면 빼고 경고를 남기며, `PLANNER.FILTER.ORDINAL_STRIPPED`를 기록한다.
- answer groundedness snapshot/verdict는 현재 단계에서는 selector를 바꾸지 않는 passive contract다. `answer.final` 선택 이유를 뒤집지 않고 debug/log/metadata로만 남긴다.

## 4. 개수 약속은 이렇게 지킨다
- `QuestionAnalysisV3.limit`는 몇 개까지 찾을지 정하는 값이며, runtime top-k의 기준값이다.
- `QuestionAnalysisV3.display_limit`는 그중 사용자에게 몇 개를 보여줄지 정하는 값이다. 찾는 개수를 직접 정하는 값은 아니다.
- `display_limit <= limit`를 강제한다.
- 사용자가 `N건`처럼 개수를 직접 말한 목록 질문은 planner가 `limit/display_limit`를 직접 정한다.
- planner 값이 없거나 비정상이면 서버 fallback이 개수를 보정하되 `MAX_TOP_K_SIZE` 상한을 넘지 않는다.
- 사용자가 개수를 분명히 말한 목록 질문에서는 planner의 `display_limit`가 그 수와 같아야 한다. 다르면 서버가 규칙 기반 개수 해석으로 다시 맞춘다.

## 5. 표시 스냅샷과 정규 근거를 이렇게 다룬다
- list/relation/comparison/series/stats 응답은 먼저 실제로 보여줄 묶음을 정한 뒤 `latest_display_snapshot`을 저장한다.
- `requested_count`는 사용자나 정책이 정한 약속된 개수이며, `docs_count`와 `canonical_count`는 실제로 관찰된 개수일 뿐이므로 그 약속을 덮어쓰면 안 된다.
- list 응답에서 `documents`가 바깥 포장 역할만 하고 `canonical_evidence`가 실제 항목 목록이면, snapshot은 항목 목록 기준으로 만든다.
- canonical item evidence가 이미 충분하면 runtime은 이것을 예외 복구로 보지 않고 기본 표시 기준으로 사용한다.
- 서버는 바깥 포장 개수에 맞춰 줄여 버리지 않고 canonical evidence를 바탕으로 display docs를 다시 만들어 list snapshot을 복구할 수 있다.
- 사용자가 개수를 분명히 말했으면 canonical recovery는 `requested_count`보다 그 명시적 개수를 먼저 따른다.
- `canonical_evidence`가 없으면 서버가 docs에서 이를 다시 만들고 `RAG.CANONICAL_EVIDENCE.DERIVED`를 기록한다.
- 복구 뒤에도 길이가 다르면 원인 파악용으로 `RAG.DISPLAY_INPUT_MISMATCH`를 남기고, 개수 비교에는 snapshot 이전의 `docs_count`, `canonical_count`, `visible_count`를 사용한다.
- hit-backed 또는 canonical-id-backed item의 title/focus anchor는 NTIS 원본 title 축을 먼저 본다. 원본 payload에 `title1`(한글 제목), `title_text`(한영 결합 제목), `title2`(영문 제목)가 있으면 detail/display anchor는 기본적으로 `title1 -> title_text -> title2` 순으로 보고, 그 다음 canonical title(`facts.title`, `meta_basic/meta_detail` title)을 fallback으로 쓴다.
- `document.title`은 display wrapper나 임시 라벨일 수 있으므로 위 title 축과 canonical title이 비어 있을 때만 마지막 fallback으로 쓴다.
- detail lookup에서 `compute_detail_coverage()`에 넘기는 입력도 같은 precedence로 `title/title_text`를 정규화해야 하며, thin doc의 표시 라벨(`1. 김봉준`)이 `[Reference Context]` title로 남으면 안 된다.
- 단, `aggregation`, `series`, `pattern_analysis`, `reverse_trace`, `multi_hop_bundle` 같은 synthetic display row는 wrapper `document.title`을 그대로 유지한다.

## 6. no-result와 엄격 실패를 이렇게 구분한다
- `lookup` 또는 `join`에서 `no_reranked`가 나오면 계약 위반으로 볼 수 있다.
- resolved seed가 있는데도 relation/join 결과가 비면, 이를 무시하고 일반 자유 질문 검색으로 넘어가면 안 된다.

## 7. 상세 커버리지는 이렇게 본다
- detail 응답은 `DetailCoverage`를 계산해 정보를 못 찾은 상태인지, 기본 정보만 있는지, 충분히 자세한지 구분한다.
- `profile_only`면 먼저 기본 프로필을 보여 주고, 더 자세한 정보만 부족하다고 안내한다.
- project detail의 raw hit가 얇아도, canonical evidence fact에 이미 `summary/goal/period/budget/outputs`가 있으면 detail coverage는 그 canonical fact를 rich-detail truth로 다시 수화할 수 있어야 한다.




- `/query/stream`의 SSE 계약은 canonical `tag="event"` envelope 하나만 사용하며, 최종 답변 truth는 `final_answer_*`와 `AnswerArtifact`에서 읽는다.
- `clarification`은 `tag="event"` + `event.kind="clarification"`로만 노출하고, visible message는 `event.content`와 `event.meta.clarification.message`에 같은 값으로 채운다.


## 8. answer context는 이렇게 나눈다
- retrieval이 만든 RagResult.context는 answer generation용 공식 source of truth다.
- answer generation은 retrieval이 넘긴 answer_context_text가 있으면 이를 그대로 [제공된 정보] 슬롯에 넣고, 없을 때만 canonical_evidence를 fallback으로 렌더링한다.
- retrieval bundle/state는 model-facing `answer_context_text`와 log-only `debug_answer_context_text`를 분리한다. 모델용 context는 `# 출처 N.` 블록과 사용자용 한국어 라벨만 사용한다.
- 시스템 프롬프트와 human prompt 슬롯 이름은 [질문 요약], [원본 질문], [제공된 정보] 계약을 따른다.
- canonical_evidence는 memory, follow-up, display snapshot, detail/focus entity 복원용 artifact로 유지하며, retrieval이 이미 만든 answer context를 다시 얇게 재구성하는 용도로 우선 사용하지 않는다.

## 9. planner V2는 이렇게 유지한다
- stagewise planner는 `surface_signals -> stage1 -> locked_strategy -> stage1.5 -> stage2 -> stage2 validation/retry -> regate -> assemble` 순서를 따른다.
- `surface_signals`는 개수, 연도, labeled id token, follow-up cue 같은 literal signal만 좁고 결정적으로 추출해야 하며, 이 단계에서 LLM 의미 보정을 섞지 않는다.
- planner domain card(`collections_card`, `id_semantics_card`, `filter_semantics_card`, `perf_tag_card`, `field_reliability_card`)는 stage별 prompt가 참조하는 명시적 입력 자산이다.
- planner prompt는 stage별 card manifest를 통해 필요한 카드만 로드해야 하며, `relationship_semantics_card`는 stage1/stage1.5/stage2에 모두 연결돼야 한다.
- prompt template rendering은 fail-open 문자열 치환이 아니라 required placeholder 검증을 거쳐야 하며, placeholder가 비면 planner runtime은 fail-close 한다.
- planner system prompt asset에는 request-scoped runtime input(`locked_strategy`, `surface_signals`, `entity_role_plan`, `validation_hints`, `previous_output`, `user_query`)을 하드코딩하지 않고 human message 입력으로만 전달한다.
- stage1은 coarse intent 분류만 맡고, ids_map·filters·retrieval_query 같은 세부 슬롯은 stage2 책임으로 남긴다.
- stage1.5는 entity role, must_keep_terms, semantic_kind, perf_type_policy 같은 보조 결정을 정리해 stage2 validation이 broad query와 explicit query를 구분할 수 있게 한다.
- stage2는 `locked_strategy`를 바꾸지 않고 slot을 채우는 단계이며, retrieval_query와 filters를 실행 가능한 형태로 구체화한다.
- stage2 validation은 people/org/year/perf_type/must_keep_terms가 retrieval_query나 filters에서 사라지지 않았는지 deterministic guard로 검증한다.
- broad_history + explicit_only 조합처럼 broad query로 남겨야 하는 경우에는 perf detail로 다시 좁히지 않는다.
- stage2 validation은 최대 한 번만 retry한다.
- retry 뒤에도 실패하면 runtime은 missing people/org/year/must_keep_terms를 exact term 기준으로 한 번 더 deterministic repair 한다.
- deterministic repair는 `mode`, `relation`, `join_key_mode`, `target_cols`, ids_map을 바꾸지 않으며, SEARCH에서는 server-side filter를 추가하지 않고 retrieval_query만 복원한다.
- broad history query에서는 generic history 표현이 validation hard-error 축은 아니어도, deterministic repair가 retrieval query에서 사용자의 semantic cue(`활동이력`, `활동내역` 등)를 다시 살려 raw-query fallback 없이 broad-history 방향을 유지할 수 있어야 한다.
- deterministic repair 뒤에도 실패하면 마지막으로 `retrieval_query=question` raw-query fallback으로 돌아가되 살릴 수 있는 filters와 limit는 유지한다.
- broad history query의 `must_keep_terms`에서는 `20건`, `3건`, `5명` 같은 count 표현과 generic history 표현을 강제 보존 축으로 다루지 않는다. count는 `explicit_count -> limit/display_limit` 계약으로만 보존한다.
- quoted title 질의에서는 제목 구절 자체를 `must_keep_terms`와 retrieval_query 축에서 잃지 않아야 한다.
- runtime legality guard는 planner 출력이라도 그대로 수용하지 않고, explicit perf id 없는 perf detail이나 explicit anchor 없는 relation, broad people/org query의 무리한 JOIN 같은 불법 전략을 막는다.
- retrieval query의 실행 기준 truth는 `resolved_retrieval_query`이며, dense/sparse/hybrid 경로 모두 이 값을 공통 입력으로 사용한다.
- people/org lookup에서는 planner가 잡은 사람명, 기관명, 기관 role 힌트가 nested server-side filter로 실제 컴파일되어야 한다. broad history people query를 tag-only qfilter로 흘려보내면 계약 위반이다.
- `participant_researcher_name`와 `people_affiliation_org_name`가 함께 있으면 `prtcp_mp` 같은 nested 객체 안에서 same-object conjunctive semantics를 사용해야 한다. 즉 사람명 축은 `must`, affiliation org 확장어는 내부 `should + min_should=1` gate를 가진 `must`로 묶는다.
- planner filters가 `participant_researcher_name`, `people_affiliation_org_name`, role-scoped org filter를 만들었으면, merged normalized intent도 같은 축의 `people_terms`, `people_affiliation_org_terms`, `org_terms/org_role`를 잃지 않아야 한다. 이 invariant가 깨지면 fail-fast debug log를 남긴다.
- people/org list에서 `documents`가 collection wrapper이고 `canonical_evidence`가 실제 item list면, display와 snapshot truth는 canonical item axis를 우선 사용한다.
- reranked 결과는 display snapshot, reference context, prompt context로 내려가기 전에 structured result constraint를 한 번 더 통과해야 한다. 사람/기관 structured constraint를 만족하지 않는 item은 최종 visible truth에서 제거한다.


## 10. Topic Gate and Detail Evidence Notes
- broad topic list/stats queries start from `SEARCH`. `action=list|stats` alone must not force `LOOKUP`; only a legal structured gate or explicit seed may upgrade the mode.
- stage2 `filters` are compiler input, not execution truth. If people/org role evidence is missing, invalid structured filters are dropped and their terms are salvaged into `retrieval_query`.
- follow-up anchor locks such as `project_key_policy=anchor_locked_*` remain immutable across planner merge unless a stronger explicit execution truth replaces them.
- detail cache/coverage is evidence truth, not the final narrated answer. Normal detail responses keep `answer_artifact=None` and pass `detail_contract_context` through `answer_context_text` for LLM narration.
- `detail_contract_context`는 내부 narration input이며, `[detail_evidence]`, `entity_kind:`, `requested_fields:` 같은 scaffold를 최종 사용자 답변에 그대로 복사하면 계약 위반이다.
- detail follow-up에서는 prompt-safe source block만 `answer_context_text`로 보내고, `[detail_evidence]`/`missing_fields:` 같은 내부 scaffold는 `debug_answer_context_text`와 로그에만 남긴다.
- entity kind and detail cache keys must prefer canonical id axes (`pjt_id/pjt_no` before people/org ids) so mixed keys like `people:pjt_id:*` are illegal.

## 11. pre-planner scope resolution은 이렇게 본다
- `request_facade`는 planner 전에 `scope_resolver`로 현재 질문의 scope를 먼저 분류한다. P0 기준 최소 분류값은 `fresh_search`, `reference_followup`, `child_entity_followup`, `scope_reset`, `ambiguous_followup`이다.
- `DisplayItem`과 `FocusEntity`는 문자열 연구자 목록과 별도로 `child_refs`를 보존한다. P0에서는 `people` child만 채우고, 기준 seed는 `ids_map.person_no`다.
- 직전 `project` 상세의 child researcher 이름이 질문에 exact unique match되고 usable `person_no`가 있으면 `source=detail_participant_match`인 `people` anchor로 승격한다.
- child researcher anchor가 resolve되면 planner 전후 모두 `normalized_intent.ids_map.person_no`를 유지해야 하며, 사람이름은 `people_terms`에 보조로만 병합한다.
- child researcher follow-up의 execution truth는 broad name search가 아니라 exact id 경로다. 즉 `person_no -> people_ids -> prtcp_mp.hm_id must`가 진실원이고, `people_terms`는 이 exact gate를 넓히면 안 된다.
- `전체 기준으로`, `이전 거 말고`, `방금 거 무시`, `이전 조건 무시` 같은 reset cue는 local display/focus anchor를 비우고 fresh search로 내려가야 한다.
- P1 기준부터 `ConversationViewState`는 `active_scope`를 함께 보존한다. `active_scope`는 `result_set`, `focus`, `child_anchor`, `parent_chain`, `scope_kind`를 들고, `latest_display_snapshot` / `latest_focus_entity`는 하위 호환 mirror로만 유지한다.
- `active_scope.focus`는 현재 상세 truth, `active_scope.child_anchor`는 현재 상세 내부에서 승격된 child entity truth다. detail focus와 child anchor를 같은 슬롯에 덮어쓰지 않는다.
- `scope_resolver`의 공식 분류값은 `fresh_search`, `reference_followup`, `child_entity_followup`, `refinement_followup`, `scope_reset`, `ambiguous_followup` 여섯 가지다.
- 분기 우선순위는 `explicit id -> reset cue -> exact child anchor -> reference/source/ordinal/deictic -> refinement -> ambiguous -> fresh`다.
- `ChildEntityRef.kind`는 `people | org | perf`를 지원한다. P1부터 `prtcp_org[]`와 linked outputs/perf summary도 child ref 축으로 저장할 수 있으며, exact seed가 있는 경우에만 child anchor로 승격한다.
- `Execution Constraint Compiler`는 planner 앞뒤에서 같은 규칙으로 `resolved_anchor -> normalized_intent.ids_map`을 다시 심는다. `people -> person_no`, `org -> org_id/org_code/biz_no`, `perf -> rst_id/doi/issn`, `project -> pjt_id/pjt_no`가 exact truth다.
- exact seed가 있을 때 이름/기관명/성과명은 설명성 보조축일 뿐이다. `people_terms`, `org_terms`, `title` 같은 보조 term은 exact gate를 widen하는 근거가 될 수 없다.
- scope ambiguity는 broad retrieval이나 direct-answer로 우회하지 않고 `clarification_required` 상태와 structured clarification payload로 내려간다. 최소 payload shape는 `clarification_type`, `message`, `candidates`, `resume_token`이다.
- `workflow_nodes.node_rule_precheck()`는 인사/짧은 질의만 rule로 처리하고, ambiguous follow-up 차단은 `scope_resolver`와 retrieval short-circuit clarification 계약으로 수렴한다.
