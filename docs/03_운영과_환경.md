# 운영과 환경

이 문서는 운영 triage와 runtime 환경 설정을 한 문서로 묶은 버전입니다.

## 1. 운영 기본 원칙

- retrieval correctness가 answer wording보다 먼저다.
- planner invalid / contract violation은 strict fail-close다.
- retrieval failure를 empty success로 위장하지 않는다.
- chat UX 문제는 retrieval correctness를 확인한 뒤 본다.

## 2. 빠른 triage 순서

### 1) 질의 / intent 확인
확인 로그:
- `REQ.START`
- `PLANNER.PIPELINE`

확인 필드:
- raw query
- `NormalizedIntent`
- explicit identifier seed 존재 여부
- candidate exact-key 존재 여부

정상 신호:
- broad topic / exact lookup / relation intent가 예상 retrieval family로 매핑된다.
- cheap precheck는 안전한 힌트만 제공한다.

의심 신호:
- non-id hint가 planner를 우회한다.
- exact-key candidate가 topic-like routing으로 떨어진다.

주요 파일:
- `apps/api/services/request_facade.py`
- `apps/core/query_intent.py`
- `apps/core/pipeline_steps.py`

### 2) 전략 확인
확인 로그:
- `PLANNER.ASSEMBLE`
- `RAG.PLAN`

확인 필드:
- `mode`
- `relation`
- `join_key_mode`
- `target_cols`
- `strategy_summary`

정상 신호:
- `SEARCH / LOOKUP / JOIN`이 결정적으로 고정된다.
- execution은 `strategy_summary`를 runtime truth로 사용한다.

의심 신호:
- planner layer와 execution layer가 서로 다르게 보인다.
- runtime이 raw text에서 전략을 다시 만드는 것처럼 보인다.

### 3) 필터 compile 확인
확인 로그:
- `RAG.FILTER.COMPILED.QDRANT`
- `RAG.COL.RETRIEVE`

확인 포인트:
- must / should 구조
- identifier / role filter
- join-key contract 보존 여부

의심 신호:
- SEARCH에 hard must가 과하게 걸린다.
- LOOKUP/JOIN에서 exact-key constraint가 사라진다.

### 4) retrieval 분포 확인
확인 로그:
- `RAG.RETRIEVE`
- `RAG.COL.STATS`

확인 포인트:
- dense / lexical hit
- collection별 hit 분포
- hybrid retrieval 동작

의심 신호:
- dense와 lexical이 모두 0이다.
- retrieval이 한쪽 약한 경로에만 갇혀 있다.

### 5) 근거와 컨텍스트 확인
확인 로그:
- `RAG.RESULT.TOP`
- `RAG.CONTEXT`
- `RAG.CTX`

확인 포인트:
- `canonical_evidence`
- `render_profile`
- `output_type`

의심 신호:
- canonicalization 과정에서 `pjt_id`, `pjt_no`, 기관 역할 의미가 흐려진다.
- render profile이 서로 다른 output shape를 하나로 뭉갠다.

### 6) 응답 / 스트리밍 확인
확인 로그:
- `LLM.RESULT`
- `STREAM.DONE`

확인 포인트:
- `ttft_any_ms`
- `ttft_content_ms`
- direct-answer mode stream behavior

의심 신호:
- stream 결과가 중복된다.
- reasoning이 사용자 최종 답변에 새어 나온다.

## 3. 최소 관측 포인트

기본 운영 로그:
- `REQ.START`
- `PLANNER.PIPELINE`
- `RAG.PLAN`
- `RAG.RETRIEVE`
- `RAG.RESULT.TOP`
- `RAG.CONTEXT`
- `RAG.RESULT`
- `LLM.RESULT`
- `REQ.SUMMARY`
- `REQ.ERROR`
- `REQ.END`

`REQ.SUMMARY` 해석:
- `mode`, `relation`, `target_cols`는 execution strategy 기준이다.
- `intent_payload_version`, `strategy_version`은 v3 경로에서 모두 보여야 한다.
- `planner_*` 필드는 진단용일 뿐, execution truth를 대체하지 않는다.

## 4. 빈 결과 해석 기준

함께 봐야 할 필드:
- `contract_fail_reason`
- `empty_result_policy`
- `reranked_count`

현재 기준:
- `lookup` / `join` + `reason=no_reranked` -> `normal_no_result`
- `search` + `reason=no_reranked` -> `strict_search`
- deferred hop1 0-hit, dual-branch 0-hit -> 일반 no-result

strict failure 예:
- resolved `instance/group`인데 필요한 seed가 없음
- invalid enum
- unsupported relation
- malformed payload

## 5. stagewise planner triage

권장 환경:
```bash
PLANNER_STAGE1_PROMPT_VERSION=v1
PLANNER_STAGE2_PROMPT_VERSION=v1
PLANNER_TEMPERATURE=0.0
```

핵심 로그:
- `PLANNER.STAGE1`
- `PLANNER.GATE`
- `PLANNER.STAGE2`
- `PLANNER.ASSEMBLE`
- `PLANNER.REGATE`
- `PLANNER.IDS_MAP.INVALID_VALUE`

검토 순서:
1. Stage 1: `action`, `head`, `relation_candidate`, `referential_followup`, `confidence`
2. Deterministic gate: `mode`, `relation`, `join_key_mode`, `target_cols`, `output_type`
3. Stage 2: `ids_map`, `candidate_keys`, `project_key_policy`, `join_resolution_policy`, `filters`, `retrieval_query`, `limit`
4. Assemble: 실행 전략이 하위 레이어에서 변형되지 않았는지 확인
5. Prelude: strict contract gate와 downgrade 결과 확인

## 6. 자주 보는 장애 패턴

### A. JOIN인데 결과가 0건
먼저 볼 것:
- `PLANNER.IDS_MAP.INVALID_VALUE`
- `PLANNER.REGATE`
- `candidate_keys.project_key`
- `project_key_policy`
- `join_key_mode`
- `resolved_runtime_join_mode`
- `dual_branch_used`

해석:
- `과제번호` 같은 ambiguous project key는 초기에 force-resolve하면 안 된다.
- sanitize로 resolved seed가 사라졌다면, runtime은 downgrade 또는 deferred discovery를 유지해야 한다.
- `JOIN_KEYS_MISSING`은 resolved `instance/group`에서만 합법이다.

### B. LOOKUP/JOIN no-result와 route error 구분
먼저 볼 것:
- `REQ.SUMMARY.contract_fail_reason`
- `REQ.SUMMARY.empty_result_policy`
- `REQ.ERROR.contract_fail_reason`
- `REQ.ERROR.empty_result_policy`

해석:
- `lookup/join + no_reranked`는 일반 no-result다.
- `search + no_reranked`만 strict_search다.

### C. SEARCH가 과도하게 제약됨
먼저 볼 것:
- compiled must / should 구조
- `search_filter_enabled`

해석:
- SEARCH는 recall 우선이어야 한다.
- lookup-style hard filter가 들어가면 drift를 의심한다.

### D. evidence shape mismatch
먼저 볼 것:
- `canonical_evidence`
- `render_profile`
- `output_type`

해석:
- answer generation은 canonical evidence와 render profile을 따라야 한다.
- `question_analysis`를 final execution truth처럼 쓰면 안 된다.

## 7. 환경 변수와 검증 명령

### 검증 명령
```powershell
python -m py_compile apps/api/main.py apps/api/app_factory.py apps/api/routes.py apps/api/runtime.py apps/api/services/workflow_builder.py apps/api/services/request_facade.py apps/core/query_intent.py apps/core/planner_staged.py
python -m pytest
python -m pytest -m smoke
powershell -ExecutionPolicy Bypass -File scripts/run_baseline_checks.ps1
```

### 최소 smoke baseline
```powershell
python -m pytest tests/test_api_routes_runtime.py tests/test_planner_stagewise.py tests/test_request_facade_and_context.py
```

### Redis
```bash
export REDIS_URL=redis://redis8:6379
export REDIS_TTL=3600
```

메모:
- `MEMORY_BACKEND`, `LOCAL_KV_DIR`는 활성 runtime knob가 아니다.
- `/health`는 Redis degradation을 보여줄 수 있지만, 그 이유만으로 hard readiness failure가 되지는 않는다.

### Runtime 기본값
```bash
export RAG_ENSURE_PAYLOAD_INDEX_ON_BOOT=true
```

메모:
- 하위 runtime layer는 fallback plan을 만들지 않는다.
- promotion 재시도를 수행하지 않는다.
- legacy payload-key fallback은 제거된 상태다.

### Context window
```bash
export RAG_CTX_HARD_LIMIT=24
export RAG_CTX_DOC_TOKEN_ESTIMATE=900
export RAG_CTX_HARD_LIMIT_MAX=80
```

### Join debug
```bash
export RAG_DEBUG_FORCE_JOIN_KEYS=false
```
