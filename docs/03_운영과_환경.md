# 운영과 환경

이 문서는 운영 triage 절차, 필수 로그, 기본 검증 명령, UTF-8 위생 규칙을 정리한다.

## 한 줄 요약
- 이 문서는 문제 생겼을 때 어디부터 보고, 어떤 로그와 테스트를 확인하고, 어느 기준을 source of truth로 삼아야 하는지 빠르게 찾게 해주는 운영 안내서다.

## 이 문서를 읽을 사람
- 운영자, 개발자, QA
- PM이나 비개발자는 상단 요약과 `9.1 외부 API 계약`까지만 읽어도 현재 구조를 따라갈 수 있다.

## 이 문서에서 바로 찾을 수 있는 것
- 가장 먼저 볼 로그
- baseline entrypoint와 수동 triage subset
- streaming / debug 응답 계약
- planner defaults와 manifest owner

## 지금 챙길 것
- baseline entrypoint는 `scripts/run_baseline_checks.ps1`이고, owner는 `apps/api/contracts/repo_manifest.py`다.
- triage는 `REQ.START -> PLANNER.* -> RAG.* -> LLM.RESULT -> REQ.SUMMARY` 순서로 보는 것이 가장 빠르다.
- `/query/stream`은 canonical SSE event 계약을 유지해야 하고, terminal 구간은 `clarification` 또는 `answer.final` 뒤에 `reference.set`, `done`으로 끝나야 한다.

## 현재 우선 리스크
- repo 전용 Python environment가 없으면 baseline 스크립트와 pytest subset을 현재 shell에서 끝까지 검증할 수 없다.
- source-reference follow-up과 child anchor처럼 follow-up 해석 품질은 planner보다 runtime upstream에서 흔들리기 쉽다.
- 운영 문서가 코드보다 늦게 갱신되면 잘못된 smoke 경로나 오래된 로그 해석을 따라가게 된다.

## 지금 확인할 로그/테스트
- 로그: `REQ.START`, `PLANNER.PIPELINE`, `RAG.RETRIEVAL_QUERY.RESOLUTION`, `RAG.RESULT`, `LLM.RESULT`, `REQ.SUMMARY`
- baseline: `powershell -ExecutionPolicy Bypass -File scripts/run_baseline_checks.ps1`
- 수동 triage subset: `tests/test_planner_stagewise.py`, `tests/test_api_routes_reference_payload.py`, `tests/test_runtime_helpers_stream_bypass.py`

## 다음 문서 업데이트 트리거
- planner defaults, baseline inventory owner, streaming contract, route/debug payload shape가 바뀌면 이 문서를 바로 갱신한다.
- 운영 로그 이름이나 우선순위가 바뀌면 예시 로그 순서도 함께 갱신한다.

## 1. 문제 생기면 먼저 볼 것

- retrieval correctness를 answer wording보다 우선한다.
- planner invalid 또는 contract violation은 strict fail-close로 본다.
- retrieval failure를 empty success로 포장하지 않는다.
- runtime이 planner truth를 임의로 재해석하지 않도록 본다.

## 2. 깊게 triage할 때는 이 순서를 따른다

### 1) 요청과 intent 확인

확인 로그:
- `REQ.START`
- `PLANNER.PIPELINE`

확인 항목:
- raw query
- `NormalizedIntent`
- explicit identifier seed 존재 여부
- candidate exact-key 존재 여부

주요 확인 파일:
- `apps/api/services/request_facade.py`
- `apps/core/query_intent.py`

### 2) assembled strategy 확인

확인 로그:
- `PLANNER.ASSEMBLE`
- `RAG.PLAN`

확인 항목:
- `mode`
- `relation`
- `join_key_mode`
- `target_cols`
- `strategy_summary`

판단 기준:
- `SEARCH`, `LOOKUP`, `JOIN`이 planner 의도대로 유지되는지 본다.
- execution이 `strategy_summary`를 runtime truth로 쓰는지 본다.

### 3) filter compile 확인

확인 로그:
- `RAG.FILTER.COMPILED.QDRANT`
- `RAG.COL.RETRIEVE`

확인 항목:
- must / should 구조
- identifier / role filter
- join-key contract 보존 여부

### 4) retrieval 분포 확인

확인 로그:
- `RAG.RETRIEVE`
- `RAG.COL.STATS`

확인 항목:
- dense / lexical hit
- collection별 hit 분포
- hybrid retrieval 동작

### 5) evidence shaping 확인

확인 로그:
- `RAG.RESULT.TOP`
- `RAG.CONTEXT`
- `RAG.CTX`

확인 항목:
- `canonical_evidence`
- `render_profile`
- `output_type`
- `docs_kind`, `canonical_kind`, `display_source`, `requested_count_source`

판단 기준:
- canonicalization 과정에서 `pjt_id`, `pjt_no`, 기관 역할 의미가 섞이지 않아야 한다.
- `output_type`에 맞는 evidence presentation shape가 유지되어야 한다.

### 6) 답변과 스트리밍 확인

확인 로그:
- 서버 기동 시 `[request_overrides] Oracle defaults connector configured`
- `REQ.ORACLE.DEFAULTS`
- `LLM.RESULT`
- `STREAM.DONE`

확인 항목:
- `ttft_any_ms`
- `ttft_content_ms`
- direct-answer mode stream behavior
- `solar_fail_reasons`, `gemma_fail_reasons`에 `internal_context_leak`가 찍히는지 여부
- Triton answer-generation 경로에서는 request override(`Top-K`, `Top-P`, `Temperature`)와 wrapper 시그니처가 일치하는지 함께 본다.
- Solar/vLLM answer-generation 경로에서는 `top_k`가 OpenAI-compatible `extra_body`로 실제 전달되는지 함께 본다.
- 요청 payload에 값이 없으면 Oracle `IRD_PARAM(PARAM_NM, PARAM_VAL)`에서 기본값을 읽고, 그것도 없을 때만 기존 ENV/code default로 내려가는지 함께 본다.
- 서버 기동 직후 Oracle defaults connector가 어느 host/service/table을 보게 되어 있는지 부팅 로그에서 먼저 확인한다.
- 요청 처리 중에는 `REQ.ORACLE.DEFAULTS`에서 Oracle lookup 시도 여부, 성공/실패 상태, 로드된 key 수, request/oracle source 분포를 함께 본다.

## 3. follow-up과 session state는 이렇게 읽는다

- explicit follow-up이 unresolved이면 retrieval을 short-circuit하고 `clarification` payload를 우선 확인한다.
- retrieval query drift triage에서는 identifier/year 보존 여부와 함께 `org_terms_lost`, `people_terms_lost`, `title_terms_lost`, `org_role_lost` 같은 drift guard도 함께 본다.
- search session state는 `latest_display_snapshot`, `active_result_set_kind`, `active_result_view_id`, `entity_scope`, `refinement_history`, `last_query_contract` 기준으로 해석한다.

## 4. 최소 관측 신호는 이것이다

기본 운영 로그:
- `REQ.START`
- `REQ.ORACLE.DEFAULTS`
- `PLANNER.PIPELINE`
- `FOLLOWUP.CONTEXT.RESTORED`: planner가 시도한 값과 최종으로 강제된 값을 함께 확인한다.
- 확인 필드: `attempted_base_route`, `attempted_target_cols`, `context_owner_lock`, `context_owner_lock_reason`, `final_base_route`, `final_target_cols`, `enforced_by`
- `RAG.PLAN`
- `RAG.RETRIEVE`
- `RAG.RESULT.TOP`
- `RAG.CONTEXT`
- `RAG.RESULT`
- `LLM.RESULT`
- `REQ.SUMMARY`
- `REQ.ERROR`
- `REQ.END`

`REQ.START` 해석:
- `request_overrides`는 최종 병합 결과다.
- `request_override_sources`는 각 파라미터의 출처를 나타내며 `request` 또는 `oracle` 값을 가진다.

`REQ.ORACLE.DEFAULTS` 해석:
- `oracle_lookup_status`는 `loaded`, `empty`, `query_failed`, `import_failed`, `skipped_all_request_values_present`, `disabled` 중 하나로 본다.
- `oracle_lookup_attempted=1`이면 실제 Oracle defaults lookup을 시도한 것이다.
- `oracle_loaded_key_count`, `oracle_loaded_keys`로 IRD_PARAM에서 실제 반영된 기본값 범위를 본다.
- `request_override_source_counts`로 최종 merged override에서 request/oracle이 각각 몇 개 필드를 차지했는지 본다.
- `route`는 `/query/stream` 또는 `/query/debug` 중 어느 엔드포인트에서 발생했는지 나타낸다.

`REQ.SUMMARY` 해석:
- `mode`, `relation`, `target_cols`는 execution strategy 기준이다.
- `intent_payload_version`, `strategy_version`은 v3 경로 기준으로 본다.
- `planner_*` 필드는 진단용이며 execution truth를 대체하지 않는다.
- `REQ.SUMMARY.target_cols`는 execution strategy 기준 최종 truth다. planner가 시도한 값은 `planner_target_cols`로만 따로 본다.

## 5. planner를 깊게 볼 때는 여기서 본다

권장 환경:

```bash
PLANNER_STAGE1_PROMPT_VERSION=v2
PLANNER_STAGE15_PROMPT_VERSION=v1
PLANNER_STAGE2_PROMPT_VERSION=v2
PLANNER_TEMPERATURE=0.0
ORACLE_PARAM_USER=...
ORACLE_PARAM_PASSWORD=...
ORACLE_PARAM_DSN=...
```

중점 로그:
- `PLANNER.STAGE1`
- `PLANNER.GATE`
- `PLANNER.STAGE2`
- `PLANNER.STAGE2.VALIDATION_FAILED`
- `PLANNER.STAGE2.DETERMINISTIC_REPAIR`
- `PLANNER.STAGE2.RAW_QUERY_FALLBACK`
- `PLANNER.ASSEMBLE`
- `PLANNER.REGATE`
- `PLANNER.IDS_MAP.INVALID_VALUE`

검토 순서:
1. Stage 1: `action`, `head`, `relation_candidate`, `referential_followup`, `confidence`
2. Deterministic gate: `mode`, `relation`, `join_key_mode`, `target_cols`, `output_type`
3. Stage 2: `ids_map`, `candidate_keys`, `project_key_policy`, `join_resolution_policy`, `filters`, `retrieval_query`, `limit`
4. Retrieval query resolution: `raw_query`, `planner_query`, `selected_search_query`, `query_resolution_reason`, `anchor_present`, `anchor_source`, `anchor_reference_kind`, `anchor_entity_key`, `anchor_query_repaired`
   - source-reference follow-up이면 `anchor_reference_kind`와 `seed_source`가 `reference_context_source_reference` 계열로 맞물리는지 함께 본다.
5. Assemble: 하위 레이어에서 전략 의미가 바뀌지 않았는지 확인
6. Prelude: strict contract gate와 downgrade 결과 확인

추가 해석 기준:
- `PLANNER.STAGE2.VALIDATION_FAILED` / `PLANNER.STAGE2.RETRY_FAILED`의 `reason_code=prompt_miss`는 prompt가 must-keep 축을 보존하지 못한 경우다.
- `PLANNER.STAGE2.DETERMINISTIC_REPAIR`는 prompt miss 뒤 runtime이 exact term만 복원한 경우다.
- `PLANNER.STAGE2.RAW_QUERY_FALLBACK` 또는 `RAG.RETRIEVAL_QUERY.RESOLUTION.query_resolution_reason=raw_query_fallback_applied`는 마지막 보호장치가 동작한 경우다.

## 6. 자주 실패하는 패턴을 이렇게 구분한다

### A. JOIN인데 결과가 0건

먼저 볼 것:
- `PLANNER.IDS_MAP.INVALID_VALUE`
- `PLANNER.REGATE`
- `candidate_keys.project_key`
- `project_key_policy`
- `join_key_mode`
- `resolved_runtime_join_mode`
- `dual_branch_used`

해석:
- 과제번호 같은 ambiguous project key를 무리하게 force-resolve하면 안 된다.
- sanitize 과정에서 resolved seed가 사라졌다면 runtime downgrade 또는 deferred discovery 여부를 확인한다.

### B. LOOKUP/JOIN no-result와 route error 구분

먼저 볼 것:
- `REQ.SUMMARY.contract_fail_reason`
- `REQ.SUMMARY.empty_result_policy`
- `REQ.ERROR.contract_fail_reason`
- `REQ.ERROR.empty_result_policy`

해석:
- `lookup/join + no_reranked`는 일반 no-result다.
- `search + no_reranked`는 `strict_search`로 본다.

### C. SEARCH가 과도하게 좁아짐

먼저 볼 것:
- compiled must / should 구조
- `search_filter_enabled`

해석:
- SEARCH는 recall 우선이어야 한다.
- lookup-style hard filter가 들어가면 drift를 의심한다.

### D. answer-generation override 계약 불일치

먼저 볼 것:
- `REQ.ERROR.reason`
- `generate_answer_gemma` 스택트레이스
- `apps/core/triton_llm.py`, `apps/core/triton_client.py`, `apps/core/openai_compat_llm.py` 의 `top_k` 전달 계약

해석:
- `/query/stream` 에서 `Top-K` override가 들어오면 Gemma/Triton과 Solar/vLLM 경로가 같은 의미로 이를 수용해야 한다.
- 한 provider만 `top_k`를 실제 요청에 싣고 다른 provider는 무시하면, 로그와 실험 결과 해석이 모두 드리프트한다.
- 상위 계층 테스트가 통과해도 provider wrapper 시그니처나 request body 구성이 stale이면 스트리밍 단계에서 실패하거나 조용한 무시가 발생한다.

### E. evidence shape mismatch

먼저 볼 것:
- `canonical_evidence`
- `render_profile`
- `output_type`

해석:
- answer generation은 canonical evidence와 render profile을 따라야 한다.
- `question_analysis`를 final execution truth처럼 쓰면 안 된다.

## 8. UTF-8 사고를 피하려면

- 모든 문서와 한글 포함 소스는 UTF-8로 저장한다.
- 한글 파일을 shell 문자열 치환으로 통째로 다시 쓰지 않는다.
- `Get-Content -Raw` 뒤 `Set-Content`로 전체 저장하는 방식은 금지한다.
- 한글 파일은 `apply_patch` 같은 최소 라인 패치 방식으로 수정한다.
- prompt loader는 UTF-8로 읽은 system prompt 선두의 BOM(`\ufeff`)을 제거해야 하며, model-specific override prompt도 같은 규칙을 따른다.
- 수정 후에는 다음을 반드시 확인한다.
  - 깨진 한글, mojibake, `?` 대체 문자 존재 여부
  - 의도치 않은 대량 diff 여부
  - 기능 변경과 인코딩 복구가 섞여 있으면 검토 가능하게 구분됐는지 여부

## 9. Streaming event 계약

- short-circuit 응답(detail cache, detail profile, clarification, no-result, degraded error)의 truth는 항상 `AnswerArtifact`다.
- `/query/stream`의 route 계층은 terminal user-visible payload(`clarification` 또는 `answer.final`) 1회와 `done` 1회를 보장해야 한다.
- `answer.chunk`는 실제 content가 발생했을 때만 보낸다.
- `/query/stream`은 canonical `tag="event"` envelope 하나만 사용한다. 초기 handshake는 `conversation` event, 진행 상태는 `status` event로 해석한다.
- stream `answer.chunk` event의 provider 표기는 canonical event 기준 `model_key="solar"` 또는 `model_key="gemma"`를 유지한다.
- `/query/stream`의 terminal visible payload는 `clarification`, `answer.final`, guard error(`MISSING_FINAL_ANSWER`) 중 하나를 먼저 내보낸 뒤, canonical `reference.set` 1회와 `done` 1회로 끝나야 한다.
- `reference` payload의 source-of-truth는 `selected_answer_artifact.references`가 최우선이고, 비어 있으면 retrieval evidence(`retrieval_bundle.items`, `canonical_evidence`)를 먼저 사용한 뒤 마지막으로 `context` hit 문서로 fallback한다. 답변 텍스트를 다시 파싱해서 citation을 추정하지 않는다.
- route는 state가 dict든 object든 같은 accessor 규칙으로 `final_answer_text`와 `final_answer_artifact`를 읽어야 한다.
- canonical clarification event는 `tag="event"` + `event.kind="clarification"`를 사용하고, `event.content`에는 사용자에게 그대로 보여줄 visible message가 채워져야 한다.
- degraded final도 별도 flat shape 없이 canonical `answer.final` event `meta`와 `done` event `meta`로만 전달한다.

### 9.1 외부 API 계약

#### 공통 요청 바디
- `POST /query/stream`
- `POST /query/debug`
- `Content-Type: application/json`
- 요청 키는 아래 JSON key를 그대로 사용한다.

```json
{
  "question": "질문 문자열",
  "conversation_id": "선택값, 기존 대화 유지 시 사용",
  "Temperature": 0.2,
  "Top-P": 0.95,
  "Max-Token": 1024,
  "Top-K": 20,
  "RAG_MIN_DENSE_SCORE": 0.3,
  "RAG_TOPK_DENSE": 50,
  "RAG_W_LEX": 0.4,
  "RAG_TOPK_LEX_CAND": 200
}
```

- 필수 필드: `question`
- 선택 필드: 나머지 전부
- `conversation_id`를 보내지 않으면 서버가 새 값을 생성한다.

#### `/query/stream` 응답 계약
- 응답 타입: `text/event-stream`
- 모든 SSE frame은 canonical envelope 하나만 사용한다.

```json
{
  "tag": "event",
  "event": {
    "kind": "answer.chunk",
    "request_id": "conversation-uuid-suffix",
    "seq": 3,
    "model_key": "solar",
    "content": "부분 응답 텍스트",
    "meta": {}
  }
}
```

- 공통 필드
  - `tag`: 항상 `"event"`
  - `event.kind`: 이벤트 종류
  - `event.request_id`: 서버가 생성한 요청 식별자
  - `event.seq`: 같은 stream 안에서 단조 증가하는 순번
  - `event.model_key`: 모델 연관 이벤트일 때 `solar` 또는 `gemma`, 아니면 `null`
  - `event.content`: 사용자 표시용 텍스트가 있을 때 사용
  - `event.meta`: 구조화된 부가 정보

#### `/query/stream` event kind 목록
- `conversation`
  - 최초 1회
  - `event.meta.conversation_id: string`
- `status`
  - 현재는 `ainvoke` 경로에서 진행 상태용으로 사용
  - `event.meta.status: "retrieve"`
- `answer.chunk`
  - 모델 streaming token
  - `event.model_key: "solar" | "gemma"`
  - `event.content: string`
- `clarification`
  - 후속질문/재지정 요청
  - `event.content: 사용자에게 그대로 보여줄 문구`
  - `event.meta.clarification: { clarification_type, message, candidates, resume_token, ... }`
  - `event.meta.clarification.message`와 `event.content`는 같은 visible message를 사용한다.
- `answer.final`
  - 최종 표시 답변
  - `event.content: 최종 답변 문자열`
  - `event.meta.answer_kind: string`
  - `event.meta.user_visible_final_required: boolean`
  - 필요 시 `event.meta.error_code`, `event.meta.reason`, `event.meta.degraded`
  - stream metric 계열(`content_chars`, `stream_content_emitted_chunks`, `ttft_*`)도 함께 포함될 수 있다.
- `reference.set`
  - 참고 문서 목록
  - `event.meta.references: [{ tag, id, title }]`
  - route는 `context`만 보지 않고 selected artifact / retrieval evidence fallback으로 이 리스트를 채운다.
- `error`
  - 비복구 에러
  - `event.meta.error`, `event.meta.error_code`, `event.meta.reason`
- `done`
  - terminal event
  - 성공 시 `meta`는 비어 있을 수 있다.
  - degraded 종료면 `event.meta.degraded=true`
  - error 종료면 `event.meta.error=true`

#### `/query/stream` 소비 순서 규칙
- 첫 frame은 `conversation`
- `ainvoke` 경로면 초반에 `status`
- 중간에는 0개 이상의 `answer.chunk`
- terminal 구간은 `clarification`, `answer.final`, `reference.set`, `done` 조합으로 온다.
- `reference.set`는 `selected_answer_artifact.references`, retrieval evidence, `context`를 같은 source-of-truth 체인으로 사용해야 하며, `context=[]`여도 selected artifact나 canonical retrieval evidence가 있으면 빈 리스트가 아니어야 한다.
- consumer는 반드시 `done`을 terminal로 해석한다.
- 사용자에게 보여줄 최종 문구는 `answer.final.content`를 기준으로 한다.
- 후속 질문 안내가 필요하면 `clarification.content`를 우선 표시한다.

## 10. planner defaults와 owner는 여기서 확인한다
- default planner prompt versions are `PLANNER_STAGE1_PROMPT_VERSION=v2`, `PLANNER_STAGE15_PROMPT_VERSION=v1`, `PLANNER_STAGE2_PROMPT_VERSION=v2`.
- authoritative owner는 `apps/api/contracts/repo_manifest.py`다. `app_factory`, `request_facade`, `scripts/run_baseline_checks.ps1`는 같은 manifest를 읽어야 한다.
- planner triage now starts with `PLANNER.SIGNALS`, then `PLANNER.STAGE1`, `PLANNER.STAGE15`, `PLANNER.STAGE2`, `PLANNER.STAGE2.VALIDATION_FAILED` or `PLANNER.STAGE2.RETRY_FAILED`, and finally `PLANNER.ASSEMBLE`.
- query execution truth is `resolved_retrieval_query`. When triaging retrieval drift, compare `raw_query`, `planner_query`, `resolved_retrieval_query`, and `actual_retrieval_query`.
- `RAG.RETRIEVAL_QUERY.ACTUAL` must show the exact query passed to the retriever. `RAG.RETRIEVAL_QUERY.MISMATCH` is an error signal and should stay absent in normal runs.
- planner validation retry is internal planner recovery, not runtime reinterpretation. If retry fails, expect conservative fallback with original question text as retrieval query.

## 11. scope / anchor 운영 신호를 이렇게 본다
- `SCOPE.DECISION`: planner 전 scope 분류 결과를 남긴다. `followup_type`, `reset_requested`, `needs_clarification`, `resolved_anchor_source`, `resolved_anchor_kind`를 먼저 본다.
- `FOLLOWUP.PARTICIPANT_ANCHOR.RESOLVED`: 직전 project detail의 child researcher가 exact anchor로 승격된 경우다. `person_no`, `person_name`, `source_project_pjt_id`, `source_project_pjt_no`가 함께 남아야 한다.
- `ANCHOR.AMBIGUOUS`: child researcher 이름이 중복되거나 usable id가 없어 exact anchor를 만들지 못한 경우다. broad retrieval로 넘어가기 전에 이 신호가 먼저 보여야 한다.
- `ANCHOR.ESCAPED`: `전체 기준으로`, `이전 거 말고`, `방금 거 무시`, `이전 조건 무시` 같은 reset cue로 local anchor를 해제한 경우다.
- child researcher follow-up triage에서는 `normalized_intent.ids_map.person_no -> people_ids -> prtcp_mp.hm_id must` 경로가 살아 있는지 먼저 확인한다. `people_terms`만 남고 `person_no`가 사라졌다면 widening regression이다.
## 12. Qdrant payload index warmup
- Startup source of truth is `APP_RUNTIME_CONFIG` in `apps/api/app_factory.py` and `initialize_app_runtime()` in `apps/api/runtime.py`.
- Boot-time payload index warmup now covers `KEYWORD`, `TEXT`, `INTEGER`, and `DATETIME` targets.
- Required keyword targets include `pjt_id`, `pjt_no`, `tag`, `prtcp_mp[].hm_id`, `prtcp_mp[].hm_nm`, `doc_id`, and perf `rst_id`.
- Text targets include org/title filter axes: `org_nm`, `prtcp_org[].org_nm`, `prtcp_mp[].blng_org_nm`, `title_text`, `title1`, `title2`.
- Integer/date targets include `stan_yr`, `meta_basic.stan_yr`, `dt1`, `dt2`, `meta_basic.tot_rsch_start_dt`, and `meta_basic.tot_rsch_end_dt`.
- Optional keyword targets such as `perf_id`, `paper_id`, and low-priority nested member fields must be created only after startup sampling observes the field in the collection payload.
