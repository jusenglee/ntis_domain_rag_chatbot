# 유지보수와 확장

이 문서는 현재 구조 debt와 앞으로의 retrieval robustness 확장 방향을 함께 정리한 문서입니다.

## 1. 문서 역할

- 현재 코드에서 남아 있는 구조 정리 항목을 관리합니다.
- strict contract를 깨지 않고 확장하는 방향을 정리합니다.
- 온보딩 문서가 아니라 유지보수/설계 의사결정용 문서입니다.

## 2. 현재 우선순위

### P0. strict contract 유지
- planner / contract / runtime 사이에 silent correction이 다시 들어오지 않게 막는다.
- compat fallback이 실행 기본 경로로 재유입되지 않게 막는다.
- `pjt_id`와 `pjt_no` 의미가 섞이지 않도록 검증을 유지한다.

### P1. JOIN runtime observability 정리
- `join_compile_selection`
- `hop2_key_strategy`
- `resolved_runtime_key_kind`

위 세 필드를 한 vocabulary로 유지한다.

원칙:
- Hop2 filter `_meta`를 source of truth로 본다.
- 상위 orchestration이 이 값을 다시 재해석하지 않는다.

### P1. 텍스트 무결성 / UTF-8 위생
- 문서와 핵심 코드에서 깨진 한글, mojibake, 중복/legacy 설명을 계속 제거한다.
- `tests/test_text_integrity.py` 범위에 운영 문서와 계약 문서를 우선 포함한다.

### P2. retrieval robustness 확장
- broad query
- 비교형 질의
- 복합 조건 질의
- 생략이 많은 follow-up 질의

위 유형의 대응력은 retrieval policy, reformulation, ranking, evidence shaping 계층에서 보강한다.

## 3. 확장 원칙

- planner contract는 strict baseline을 유지한다.
- `SEARCH / LOOKUP / JOIN` 경계를 흐리지 않는다.
- parser / planner / runtime이 전략 의미를 자동 보정하지 않는다.
- raw payload를 prompt에 직접 넣지 않는다.
- canonical evidence 경유 원칙을 유지한다.

## 4. 개선 축

### Query Reformulation
- retrieval 의미를 보존하는 reformulation 후보를 만든다.
- broad topic 질의는 recall 확장을 허용한다.
- exact lookup 질의는 identifier fidelity를 우선한다.

### Ambiguity Handling
- ambiguous query를 두 종류로 나눈다.
  1. planner contract 위반
  2. retrieval ambiguity

처리 원칙:
- contract violation은 fail-close
- retrieval ambiguity는 policy layer에서 다중 후보 query, soft filter, ranking diversification으로 처리

### Retrieval Expansion
- SEARCH에서만 확장 정책을 우선 허용한다.
- LOOKUP/JOIN은 precision-first를 유지한다.
- identifier semantics는 바꾸지 않는다.

### Ranking / Selection
- broad query는 recall 확보 뒤 rerank를 강화한다.
- lookup/join은 hard signal 보존을 우선한다.
- ranking은 evidence fidelity를 해치면 안 된다.

### Evidence Shaping
- robustness 개선 이후에도 source semantics를 그대로 유지해야 한다.
- `output_type`은 answer style이 아니라 evidence presentation shape다.
- 탐색형과 정확 조회형이 같은 prompt view를 무분별하게 공유하면 안 된다.

## 5. 질의 유형별 목표

| 질의 유형 | 현재 상태 | 목표 |
|---|---|---|
| exact identifier lookup | 강함 | strict precision 유지 |
| relation join | 강함 | group fallback observability 강화 |
| broad topic search | 보통 | reformulation + recall 확장 |
| complex constrained search | 보통 이하 | field-aware policy 추가 |
| comparative query | 약함 | multi-evidence retrieval / aggregation 보강 |
| follow-up query | 보통 | canonical evidence anchor 기반 보강 |

## 6. 변경 작업 원칙

- 코드 변경과 문서 변경은 같은 변경셋으로 묶는다.
- raw -> canonical -> prompt 흐름의 의미 보존을 우선한다.
- retrieval correctness가 answer style보다 우선이다.
- 단계별 흐름과 artifact handoff는 아키텍처/흐름 문서와 함께 갱신한다.
