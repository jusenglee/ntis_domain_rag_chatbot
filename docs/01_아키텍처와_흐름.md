# 아키텍처와 흐름

이 문서는 NTIS Domain RAG를 **retrieval-first 검색 시스템 + chat UX** 관점으로 설명합니다.

핵심 원칙은 간단합니다.

- 먼저 올바른 retrieval 전략을 고정한다.
- 그 전략으로 근거를 수집하고 canonical evidence를 만든다.
- 그다음에야 답변 문장, 스트리밍, 대화 UX가 붙는다.

즉, 답변 표현은 중요하지만 retrieval contract를 바꾸는 계층이 아닙니다.

## 1. 시스템의 4개 계층

### 1) 질의 이해
입력:
- 사용자 질의
- 대화 힌트
- 이전 canonical evidence

출력:
- `question_analysis`
- `intent_payload.normalized_intent`

책임:
- 질의에서 retrieval 의도를 읽는다.
- exact id, candidate key, 사람/기관/관계 신호를 정리한다.
- planner가 사용할 입력을 만든다.

금지:
- 최종 실행 전략을 여기서 멋대로 확정하지 않는다.
- raw payload를 prompt에 바로 넣지 않는다.

### 2) Retrieval 실행
입력:
- 조립된 `strategy`
- compiled filter
- runtime policy

출력:
- retrieval hit
- join hop result
- execution metadata

책임:
- SEARCH / LOOKUP / JOIN을 계약대로 수행한다.
- contract violation은 fail-close로 처리한다.
- 하위 레이어에서 새 전략을 만들지 않는다.

금지:
- `mode`, `relation`, `join_key_mode`, `target_cols`를 새로 발명하지 않는다.
- invalid strategy를 조용히 다른 strategy로 바꾸지 않는다.

### 3) 근거 조립
입력:
- retrieval hit
- execution mode / route / output_type

출력:
- `canonical_evidence`
- `render_profile`
- context text

책임:
- raw retrieval payload를 canonical schema로 정규화한다.
- `output_type`에 맞는 evidence presentation shape를 고른다.
- `pjt_id`, `pjt_no`, 기관 역할 의미를 보존한다.

금지:
- retrieval metadata 전체를 LLM에 그대로 노출하지 않는다.
- retrieval view와 prompt view를 같은 artifact처럼 다루지 않는다.

### 4) 채팅 UX
입력:
- canonical evidence
- render profile
- answer policy
- conversation state

출력:
- 사용자 응답
- stream event
- conversation memory snapshot

책임:
- retrieval 결과를 읽기 쉬운 답변으로 변환한다.
- memory, follow-up, streaming을 관리한다.
- degraded response가 필요할 때 사용자 경험을 관리한다.

금지:
- retrieval contract를 바꾸지 않는다.
- canonical evidence 없이 임의 답변을 우선하지 않는다.

## 2. 요청 1건의 처리 흐름

1. **Request ingress**
   - API route가 workflow seed를 만든다.
   - 이 단계에서는 retrieval 전략을 결정하지 않는다.

2. **질의 이해 / intent assembly**
   - `question_analysis`
   - `intent_payload.normalized_intent`

3. **planner contract / strategy assembly**
   - deterministic gate와 planner merge를 거쳐 `strategy`를 조립한다.

4. **runtime prelude / strict validation**
   - `strategy`를 검증하고 `RuntimePreludeResult`를 만든다.

5. **retrieval execution**
   - SEARCH / LOOKUP / JOIN orchestration을 수행한다.

6. **evidence assembly**
   - retrieval result를 `canonical_evidence`와 `render_profile`로 바꾼다.

7. **answer generation / chat UX**
   - canonical evidence를 바탕으로 응답을 생성하고 stream을 관리한다.

8. **response / ops summary**
   - 최종 응답과 `REQ.SUMMARY`를 남긴다.

## 3. 핵심 artifact와 소유권

### `question_analysis`
- planner artifact입니다.
- 실행 진실(execution truth)이 아닙니다.
- debug와 drift 진단에는 유용하지만, 하위 runtime이 그대로 truth처럼 쓰면 안 됩니다.

### `intent_payload.normalized_intent`
- retrieval가 소비하는 canonical 질의 객체입니다.
- query understanding의 최종 산출물이며 retrieval workflow의 기본 입력입니다.

### `strategy`
- 실행 전략의 진실입니다.
- planner merge, contract validation, runtime prelude를 통과한 최종 실행 전략입니다.

### `canonical_evidence`
- retrieval 결과 정규화의 진실입니다.
- raw retrieval payload를 prompt에 직접 넣지 않고 canonical schema로 바꾼 결과입니다.

### `render_profile`
- 표현 계약입니다.
- `output_type`에 따라 어떤 evidence shape를 만들지 결정합니다.
- 답변 문체를 정하는 객체가 아닙니다.

## 4. 단계별 관측 포인트

### 요청 시작
- `REQ.START`

### planner 파이프라인
- `PLANNER.PIPELINE`
- `PLANNER.STAGE1`
- `PLANNER.STAGE2`
- `PLANNER.ASSEMBLE`

### 전략/실행
- `RAG.PLAN`
- `RAG.RETRIEVE`
- `RAG.COL.RETRIEVE`
- `RAG.COL.STATS`
- `RAG.JOIN.POLICY`
- `RAG.JOIN.HOP1`
- `RAG.JOIN.HOP2.TOP`

### 근거/컨텍스트
- `RAG.RESULT.TOP`
- `RAG.CONTEXT`
- `RAG.CTX`
- `RAG.RESULT`

### 응답/종료
- `LLM.RESULT`
- `STREAM.DONE`
- `REQ.SUMMARY`
- `REQ.END`

## 5. 계층별 금지 사항 요약

| 계층 | 할 수 있는 일 | 하면 안 되는 일 |
|---|---|---|
| 질의 이해 | retrieval intent 조립, hint 정규화 | final runtime strategy 재결정 |
| Retrieval 실행 | contract enforcement, compile, retrieval 수행 | 새 mode / relation / join key 발명 |
| 근거 조립 | canonicalization, render profile 선택 | source semantics 변경 |
| 채팅 UX | 응답 표현, streaming, 대화 흐름 | retrieval contract 변경 |

## 6. 운영 우선순위

운영과 디버깅에서의 우선순위는 아래와 같습니다.

1. retrieval strategy correctness
2. join / filter correctness
3. canonical evidence fidelity
4. render / output correctness
5. chat UX correctness
