# 회귀 기준과 점검

이 문서는 follow-up, planner merge, retrieval short-circuit, display snapshot 계약의 회귀 포인트를 정리한다.

## 1. Follow-up 회귀
- `1번 과제의 연구자를 알려줘` 같은 ordinal follow-up가 `Reference Context` 1번 item의 `pjt_id`로 resolve되는지 확인한다.
- `그 과제의 연구자를 알려줘` 같은 deictic follow-up가 single previous item에서는 resolve되고, multiple item에서는 clarification으로 넘어가는지 확인한다.
- explicit follow-up clarification이 필요한 경우 retrieval을 short-circuit하는지 확인한다.

## 2. Sanitization 회귀
- planner filters에 `1번째`, `그`, `이번` 같은 ordinal/deictic noise가 섞여 있으면 strip되고 `PLANNER.FILTER.ORDINAL_STRIPPED` 로 기록되는지 확인한다.

## 3. Count 계약 회귀
- `반도체 분야 과제 3건을 알려줘` 같은 명시적 count list 질의에서 planner가 `display_limit=3`을 내리면 최종 visible subset도 3건으로 유지되는지 확인한다.
- invalid planner count에서도 fallback 결과 `limit/display_limit`가 `MAX_TOP_K_SIZE`를 넘지 않는지 확인한다.
- detail count 질의는 fallback이 동작해도 `limit=1`, `display_limit=1`을 유지하는지 확인한다.

## 4. Display snapshot 회귀
- 목록 응답 후 `view_state.latest_display_snapshot`이 저장되는지 확인한다.
- raw retrieval count와 visible count가 분리돼 기록되고, `RAG.COUNT_PIPELINE`/`RAG.COUNT_PIPELINE.RESULT`에서 planner limit, runtime top-k, visible count를 함께 볼 수 있는지 확인한다.
- `documents`와 `canonical_evidence` 길이가 엇갈리면 `RAG.CANONICAL_EVIDENCE.DERIVED` 또는 `RAG.DISPLAY_INPUT_MISMATCH` 로그가 남는지 확인한다.

## 5. Strict failure 회귀
- `pjt_id`와 `pjt_no`를 같은 의미로 섭지 않는지 확인한다.
- `strategy_meta.seed_source`가 follow-up truth를 대체하지 않고 보조 metadata로만 남는지 확인한다.
- unresolved explicit follow-up를 일반 retrieval로 무단 진행하지 않는지 확인한다.
