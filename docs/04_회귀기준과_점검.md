# 회귀 기준과 점검

이 문서는 골든 질의와 drift checklist를 한 문서로 합친 버전입니다.

목표는 두 가지입니다.

1. 현재 기준선이 무엇인지 빠르게 확인한다.
2. 파일별 drift 여부를 장황한 표 없이 실무적으로 점검한다.

## 1. 핵심 불변식

### 전략 불변식
- planner는 요청당 전략 1개를 고정한다.
- executor는 그 전략을 검증하고 실행하지만 새 전략을 만들지 않는다.
- `SEARCH`, `LOOKUP`, `JOIN`은 서로 다른 계약이다.
- cheap precheck는 사람/기관/역할 의미에서 planner truth를 덮어쓰지 않는다.
- ambiguous project key는 resolved `pjt_id` / `pjt_no`로 성급하게 승격하지 않는다.

### JOIN / filter 불변식
- JOIN은 legal relation intent와 legal join strategy가 필요하다.
- sanitize로 invalid seed가 제거된 뒤 strict JOIN이 억지로 남아 있으면 안 된다.
- `join_key_mode=instance` / `group`은 strict resolved-key mode다.
- `join_key_mode=deferred`는 합법 runtime 전략이다.
- group fallback은 runtime metadata에 드러나야 하며, 의미를 조용히 바꾸면 안 된다.

### evidence 불변식
- canonical evidence는 `pjt_id`, `pjt_no`, `rst_id` 의미를 각각 보존한다.
- lead / participant / affiliation organization semantics를 섞지 않는다.
- retrieval view와 prompt view는 서로 다른 artifact다.
- answer context는 canonical evidence에서 만들어진다.

### output / streaming 불변식
- `output_type`은 answer wording이 아니라 evidence presentation shape를 정한다.
- `summary`, `detail`, `list`, `stats`, `relation`, `comparison`, `series`는 서로 다른 context shape를 가진다.
- reasoning chunk가 최종 답변에 섞이면 안 된다.
- `ttft_any_ms`와 `ttft_content_ms`는 분리된 metric이다.

### v3 불변식
- `ids_map`에는 resolved identifier만 들어간다.
- `candidate_keys.project_key`는 unresolved exact project key다.
- `project_key_policy=ambiguous_or`는 exact OR exact discovery다.
- `join_key_mode=deferred`는 정상 전략이다.
- `lookup/join + no_reranked`는 `normal_no_result`다.
- `search + no_reranked`는 `strict_search`다.
- `IntentPayloadV3`와 `strategy_version="v3"`가 함께 간다.

## 2. 대표 골든 질의

| ID | 질의 | 기대 mode | 메모 |
|---|---|---|---|
| G001 | `AI 관련 과제` | `search` | 넓은 주제 탐색 |
| G002 | `1711015550 과제 상세` | `lookup` | exact project id lookup |
| G003 | `PJT-2020-1234-5678 관련 성과` | `join` | unresolved exact project key + relation cue |
| G004 | `김 연구자 참여 과제` | `lookup` | 사람 기반 lookup |
| G005 | `ETRI 논문 통계 2021 2023` | `lookup` | stats-style perf lookup |

### v3 골든 케이스
- `과제번호 a4412354543 상세` -> `LOOKUP` + `project_key_policy=ambiguous_or` + unresolved `candidate_keys.project_key`
- `과제번호 a4412354543 성과` -> `JOIN` + `join_key_mode=deferred`
- `과제고유번호 a4412354543 상세` -> resolved `ids_map.pjt_id`
- `동일과제번호 a4412354543 전체 이력` -> resolved `ids_map.pjt_no`
- numeric-only project key는 강한 라벨 없이 자동 승격하지 않는다.
- 영문+숫자 exact key는 hygiene validation을 통과하면 `candidate_keys.project_key`로 남을 수 있다.

## 3. extended runtime 점검 포인트

### comparison
- aggregation payload가 answer generation 전에 만들어지는가
- payload에 `metric`, `group_by`, `threshold`, `sort_order`, `rank_items`가 들어가는가

### series
- `output_type=series`가 metadata-only로 끝나지 않는가
- `series_key_kind`, `series_key`, `instance_projects`, `linked_perf`, `year_buckets`가 유지되는가

### reverse trace
- `perf -> project -> perf` relation chain이 runtime payload와 로그에 남는가
- hop3 follow-up이 hop1 origin performance를 중복하지 않는가

### anchor resolution
- researcher + generic org ambiguity가 summary/debug metadata에 남는가
- unresolved researcher/org pairing이 strict JOIN을 강제하지 않는가

### pattern analysis
- `query_graph_kind=pattern_analysis`가 맞게 찍히는가
- supported pattern만 runtime에서 계산되는가

### multi-hop bundle
- ambiguity가 strict JOIN 강제가 아니라 downgrade + guidance로 처리되는가
