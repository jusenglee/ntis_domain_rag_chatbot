## 2. Sanitization 회귀
- planner filters에 `1번째`, `그`, `이번` 같은 ordinal/deictic noise가 섞여 있으면 strip되고 `PLANNER.FILTER.ORDINAL_STRIPPED` 로 기록되는지 확인한다.

## 3. Count 계약 회귀
- `반도체 분야 과제 3건을 알려줘` 같은 명시적 count list 질의에서 planner가 `display_limit=3`을 내리면 최종 visible subset도 3건으로 유지되는지 확인한다.
- invalid planner count에서도 fallback 결과 `limit/display_limit`가 `MAX_TOP_K_SIZE`를 넘지 않는지 확인한다.
- detail count 질의는 fallback이 동작해도 `limit=1`, `display_limit=1`을 유지하는지 확인한다.

## 4. Display snapshot regression
- Verify that `view_state.latest_display_snapshot` is stored after list responses.
- Verify that raw retrieval count and visible count are logged separately, and that `RAG.COUNT_PIPELINE` / `RAG.COUNT_PIPELINE.RESULT` show planner limit, runtime top-k, and visible count together.
- Verify that a case like `documents=10`, `canonical_evidence=1`, `requested_count=3` keeps visible count at 3 rather than collapsing to 1.
- Verify that a case like `docs_count=1`, `canonical_count=10`, `requested_count=3`, `output_type=list` recovers from canonical item evidence and stores a 3-item snapshot.
- Verify that a case like `docs_count=1`, `canonical_count=10`, `requested_count=20`, `explicit_count=3`, `output_type=list` still recovers from canonical item evidence using the explicit count threshold.
- Verify that `DISPLAY.SNAPSHOT.BUILT` and `RAG.COUNT_PIPELINE.RESULT` log the pre-snapshot `docs_count`, `canonical_count`, and `visible_count` together.
- Verify that those logs also record `docs_kind`, `canonical_kind`, `display_source`, and `requested_count_source`.
- Verify that cardinality mismatch still emits `RAG.CANONICAL_EVIDENCE.DERIVED` or `RAG.DISPLAY_INPUT_MISMATCH`.
- If the planner retrieval query changes the original semantic axis, `RAG.RETRIEVAL_QUERY.RESOLUTION` must record `drift_detected`, `drift_reasons`, and `fallback_applied`.
- For resolved follow-up anchors in detail lookup, if the planner query becomes generic, `selected_search_query` must be repaired to an anchor-preserving compact query and the log must include `anchor_present`, `anchor_source`, `anchor_entity_key`, and `anchor_query_repaired`.
- For resolved project ordinal follow-ups like `3rd project detail`, planner drift must not add the performance axis, and the repaired lookup query must stay on the resolved project anchor.
