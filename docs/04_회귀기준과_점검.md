# 회귀 기준과 점검

이 문서는 follow-up, planner merge, retrieval short-circuit, display snapshot에서 무엇이 다시 깨지면 안 되는지 정리한다.

## 1. 후속 질문 회귀(Follow-up)
- `1번 과제의 연구자를 알려줘` 같은 말이 `Reference Context`의 1번 항목을 정확히 가리키는지 확인한다.
- `출처 2의 연구자 정보`는 display snapshot이 남아 있어도 source reference가 우선한다. resolved되면 `seed_source=reference_context_source_reference`와 `anchor_reference_kind=source_reference`가 같이 남아야 한다.
- `그 과제의 연구자를 알려줘` 같은 말은 앞에 항목이 하나일 때만 바로 해석되고, 여러 개면 다시 물어보는지 확인한다.
- 사용자의 뜻이 분명하지 않아 다시 물어봐야 할 때는 retrieval을 억지로 진행하지 않는지 확인한다.
- project anchor는 `pjt_id`와 `pjt_no`를 섞지 않고 그대로 유지하는지, planner merge 뒤에도 같은 기준이 이어지는지 확인한다.
- resolved follow-up anchor가 `focus_entity`, `strategy_meta`, `view_state.latest_focus_entity`에 같은 뜻으로 남아, 다음 detail 질문의 기준이 되는지 확인한다.
- detail cache fast-path, anchor query repair, anchor exact lookup이 모두 `normalized_intent.ids_map` 안의 현재 seed를 기준으로 움직이는지 확인한다.
- `수행기관`, `참여기관`, `소속기관`처럼 역할이 다른 기관 질문이 project anchor 기준의 detail 계약을 유지하고, 엉뚱한 목록 축으로 흔들리지 않는지 확인한다.
- follow-up detail에서 `ids_map` seed가 없으면 함부로 exact lookup으로 내려가지 않고 `RAG.DETAIL.ANCHOR.SEED_MISSING`가 남는지 확인한다.
- 같은 override 입력이 들어오면 `/query/stream`과 `/query/debug`가 같은 `request_overrides` 값을 받는지 확인한다.
- 요청 override가 없으면 Oracle `IRD_PARAM` 기본값이 `/query/stream`과 `/query/debug` 양쪽에 같은 `request_overrides`로 들어가는지 확인한다.
- 요청 override와 Oracle 기본값이 동시에 있으면 요청 값이 Oracle 값을 덮는지 확인한다.
- Gemma/Triton answer generation이 `Top-K` override를 받아도 stream 중간에 `TypeError`가 나지 않는지 확인한다.
- Solar/vLLM answer generation도 `Top-K`를 OpenAI 호환 요청 본문에 제대로 넣는지 확인한다.
- Triton sampling parameter에는 override가 있을 때만 `top_k`가 들어가는지 확인한다.
- 잘못된 override 값은 provider 호출 전에 바로 막히는지 확인한다.

## 2. 정제 회귀(Sanitization)
- planner filters에 `1번째`, `그`, `이번` 같은 말이 섞여 있으면 제거되고 `PLANNER.FILTER.ORDINAL_STRIPPED`가 남는지 확인한다.

## 3. 개수 계약 회귀(Count)
- `반도체 분야 과제 3건을 알려줘`처럼 개수를 분명히 말한 질문에서 planner가 `display_limit=3`을 내리면, 최종으로 보여주는 개수도 3건인지 확인한다.
- planner가 잘못된 개수를 내도 fallback 뒤 값이 `MAX_TOP_K_SIZE`를 넘지 않는지 확인한다.
- detail count 질문은 fallback이 동작해도 `limit=1`, `display_limit=1`을 유지하는지 확인한다.

## 4. 표시 스냅샷 회귀(Display Snapshot)
- list 응답 뒤 `view_state.latest_display_snapshot`이 저장되는지 확인한다.
- raw retrieval count와 visible count가 따로 기록되고, `RAG.COUNT_PIPELINE` / `RAG.COUNT_PIPELINE.RESULT`에 planner limit, runtime top-k, visible count가 함께 남는지 확인한다.
- `documents=10`, `canonical_evidence=1`, `requested_count=3` 같은 경우 보여주는 개수가 1로 줄지 않고 3으로 유지되는지 확인한다.
- `docs_count=1`, `canonical_count=10`, `requested_count=3`, `output_type=list` 같은 경우 canonical item evidence를 이용해 3개 항목 snapshot으로 복구되는지 확인한다.
- `docs_count=1`, `canonical_count=10`, `requested_count=20`, `explicit_count=3`, `output_type=list` 같은 경우에도 사용자가 말한 개수를 기준으로 복구되는지 확인한다.
- `DISPLAY.SNAPSHOT.BUILT`와 `RAG.COUNT_PIPELINE.RESULT`가 snapshot을 만들기 전의 `docs_count`, `canonical_count`, `visible_count`를 함께 남기는지 확인한다.
- 위 로그가 `docs_kind`, `canonical_kind`, `display_source`, `requested_count_source`도 함께 남기는지 확인한다.
- 개수 축이 맞지 않는 상황에서도 `RAG.CANONICAL_EVIDENCE.DERIVED` 또는 `RAG.DISPLAY_INPUT_MISMATCH`가 기록되는지 확인한다.
- 바깥 포장형 목록 흐름에서는 canonical item evidence가 충분할 때 `RAG.DISPLAY_INPUT_MISMATCH`보다 `RAG.DISPLAY_CANONICAL_AXIS.PROMOTED`를 우선 사용하는지 확인한다.
- planner retrieval query가 원래 질문 뜻을 바꾸면 `RAG.RETRIEVAL_QUERY.RESOLUTION`에 `drift_detected`, `drift_reasons`, `fallback_applied`가 기록되는지 확인한다.
- 해석된 후속 질문 anchor가 있는 detail lookup에서 planner query가 너무 일반적으로 바뀌면, `selected_search_query`가 anchor를 살린 compact query로 복구되고 관련 로그가 남는지 확인한다.
- `3rd project detail` 같은 resolved project ordinal follow-up에서는 planner drift가 성과 축을 추가하지 않고, 복구된 lookup query가 원래의 project anchor를 유지하는지 확인한다.
- perf 목록에서 고른 후속 질문에서는 planner merge가 `project`를 시도하더라도 `planner_service.apply_planner_strategy()`가 `base_route=perf`, `target_cols=[\"ntis_perf_v1\"]`를 최종값으로 강제하고 `FOLLOWUP.CONTEXT.RESTORED`에 attempted 값과 enforced 값을 함께 남기는지 확인한다.
- anchored detail follow-up에서 너무 일반적인 검색 질의가 나오면 anchor-locked exact lookup(`top_k=1`)으로 복구되는지 확인한다.
- perf detail follow-up에서는 `ids_map`에 `rst_id`가 있으면 exact lookup이 `rst_id`를 기준으로 유지되고, `pjt_id`로 임의 전환되지 않는지 확인한다.
- `REQ.SUMMARY.target_cols`는 planner 시도값이 아니라 final execution truth를 가리켜야 하며, planner 시도값은 `planner_target_cols`에서만 확인한다.
- 오래된 `latest_focus_entity`만 남아 있을 때는 anchor-locked exact lookup(`top_k=1`)이나 detail cache 적중을 억지로 타지 않는지 확인한다.
- hit-backed detail/project row에서 `document.title`이 `1. 김봉준` 같은 표시 라벨이어도 display snapshot과 focus entity의 title은 canonical project title을 우선하는지 확인한다.
- raw payload에 `title1/title_text/title2`가 함께 있을 때 display snapshot, focus entity, detail coverage input이 `title1`을 우선 사용하고 `document.title`로 되돌아가지 않는지 확인한다.
- `DETAIL.COVERAGE`/`[Reference Context]`를 만들기 직전의 detail coverage input도 polluted `title/title_text`를 canonical project title로 덮어써서 최종 evidence title이 표시 라벨로 남지 않는지 확인한다.
- `aggregation`, `series`, `pattern_analysis`, `reverse_trace`, `multi_hop_bundle` 같은 synthetic row는 canonical title이 있어도 wrapper title을 유지하는지 확인한다.

## 5. 엄격 실패 회귀(Strict Failure)
- detail cache, detail profile, clarification, no-result 같은 short-circuit 응답은 `AnswerArtifact`를 truth로 사용하고, live chunk가 0개여도 `answer.final` 1회와 `done` 1회가 유지되는지 확인한다.
- `pjt_id`와 `pjt_no`를 같은 의미로 섭지 않는지 확인한다.
- `strategy_meta.seed_source`가 follow-up의 기준 자체를 대신하지 않고, 보조 정보로만 남는지 확인한다.
- 아직 분명히 정해지지 않은 후속 질문을 일반 retrieval로 밀어붙이지 않는지 확인한다.
- short-circuit 경로에서 synthetic `chunk`가 있더라도 route 기준 최종 visible payload는 `answer.final`임을 확인한다.
- 비교 UI 회귀(compare UI regression)에서 `chunk` event의 provider 라벨이 Solar=`SOLAR/solar`, Gemma=`GEMMA/gemma`로 유지되는지 확인한다.
- `/query/debug`에서는 `merge_debug.selected_answer_source`, `merge_debug.selected_answer_kind`, `selected_answer_meta.answer_kind`가 서로 모순되지 않는지 확인한다.
- passive groundedness verdict가 추가돼도 selector behavior는 바뀌지 않아야 한다. unsupported `project_id/year/org_name/count`는 `selected_answer_meta`와 `final_answer_meta`에만 남고 `selected_model`을 뒤집지 않아야 한다.
- 한 모델이 `[detail_evidence]` 또는 ASCII `key: value` scaffold를 그대로 누수하면 다른 정상 모델을 고르고, 두 모델이 모두 invalid면 fallback으로 내려가는지 확인한다.

## 7. Planner V2 Regression Targets
- `collect_surface_signals()` should keep literal count, year, labeled id token, and follow-up cue extraction narrow and deterministic.
- planner prompt card loading should be stage-specific. Every required card in the prompt manifest must be registered, and `relationship_semantics_card` must be wired into stage1/stage1.5/stage2.
- planner prompt rendering should fail closed when a required placeholder is missing, while leaving JSON example braces untouched.
- planner system prompt assets must not embed request-scoped runtime placeholders. `locked_strategy`, `surface_signals`, `entity_role_plan`, `validation_hints`, `previous_output`, and `user_query` should remain human-message inputs.
- `validate_stage2_slots()` should fail when people/org/year/perf_type/must_keep_terms disappear from retrieval_query or filters.
- `validate_stage2_slots()` should treat `semantic_kind=broad_history` plus `perf_type_policy=explicit_only` as a broad query and must not reintroduce perf-type pressure just to satisfy retry hints.
- `validate_stage2_slots()` should ignore count-like broad-history terms such as `20건`, `3건`, `5명` and generic history labels when checking `missing_must_keep_terms`.
- stage2 retry가 실패해도 deterministic repair가 exact people/org/title/year term을 복원하면 raw-question fallback 없이 통과해야 한다.
- deterministic repair는 SEARCH에서는 filters를 추가하지 않고 retrieval_query만 복원해야 한다.
- broad people/org queries must not collapse into `perf + detail` unless an explicit perf id seed exists.
- stage2 validation should allow exactly one retry. If retry still fails, planner fallback should restore `retrieval_query=question` while preserving salvageable filters and limits.
- `신동구(한국과학기술정보연구원) 연구자의 활동이력` 같은 parenthesized broad-history 질의는 `people_terms_lost`, `org_terms_lost` drift를 잡아야 한다.
- `'단일 반도체물질 기반 3진 논리 게이트 개발' 과제 상세정보` 같은 quoted-title 질의는 `title_terms_lost` drift를 잡아야 한다.
- `2번 과제의 상세정보`, `출처 2의 연구자 정보` 같은 ordinal/source-reference follow-up은 eval fixture와 회귀 기준에 포함돼야 한다.
- `render_display_snapshot_text()` and `_planner_prev_context_text()` must use real newline characters so follow-up prev_context stays readable.
- retrieval workflow should return and persist `resolved_retrieval_query`, and retriever invocation should use that same value.
- `collect_surface_signals()` should not surface internal collection tags like `IRD_*` as user-facing perf type signals, and should preserve explicit parenthesized person/org mentions when normalized intent is empty.
- people/org lookup queries should compile into actual participant researcher / org nested filters. If the runtime falls back to tag-only filtering for a people query, regression tests should fail.
- `participant_researcher_name` + `people_affiliation_org_name` should compile into a same-object `prtcp_mp` nested filter where `hm_nm` is `must` and affiliation-org expansions are gated under `must(Filter(should=[...]))`.
- merged planner intent should keep `people_terms`, `people_affiliation_org_terms`, and role-scoped `org_terms/org_role` in sync with emitted structured filters, and invariant drift should emit fail-fast debug logs.
- reranked results should pass a deterministic structured post-filter before display snapshot and reference context are built. Display items, canonical evidence subset/order, prompt context, and visible count should all derive from that same filtered set.
- refusal-like merge detection should degrade answers that say the requested fact is not included, not specified, or cannot be guided from the provided information.
- internal-context leak detection should degrade answers that echo `[detail_evidence]`, internal ASCII scaffold fields, or prompt-echo text such as `질문을 입력해주세요.`
