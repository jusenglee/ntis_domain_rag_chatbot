# 회귀 기준과 점검

이 문서는 follow-up, planner merge, retrieval short-circuit, display snapshot에서 무엇이 다시 깨지면 안 되는지 정리한다.

## 1. 후속 질문 회귀(Follow-up)
- `1번 과제의 연구자를 알려줘` 같은 말이 `Reference Context`의 1번 항목을 정확히 가리키는지 확인한다.
- `그 과제의 연구자를 알려줘` 같은 말은 앞에 항목이 하나일 때만 바로 해석되고, 여러 개면 다시 물어보는지 확인한다.
- 사용자의 뜻이 분명하지 않아 다시 물어봐야 할 때는 retrieval을 억지로 진행하지 않는지 확인한다.
- project anchor는 `pjt_id`와 `pjt_no`를 섞지 않고 그대로 유지하는지, planner merge 뒤에도 같은 기준이 이어지는지 확인한다.
- resolved follow-up anchor가 `focus_entity`, `strategy_meta`, `view_state.latest_focus_entity`에 같은 뜻으로 남아, 다음 detail 질문의 기준이 되는지 확인한다.
- detail cache fast-path, anchor query repair, anchor exact lookup이 모두 `normalized_intent.ids_map` 안의 현재 seed를 기준으로 움직이는지 확인한다.
- `수행기관`, `참여기관`, `소속기관`처럼 역할이 다른 기관 질문이 project anchor 기준의 detail 계약을 유지하고, 엉뚱한 목록 축으로 흔들리지 않는지 확인한다.
- follow-up detail에서 `ids_map` seed가 없으면 함부로 exact lookup으로 내려가지 않고 `RAG.DETAIL.ANCHOR.SEED_MISSING`가 남는지 확인한다.
- 같은 override 입력이 들어오면 `/query/stream`과 `/query/debug`가 같은 `request_overrides` 값을 받는지 확인한다.
- Gemma/Triton answer generation이 `Top-K` override를 받아도 stream 중간에 `TypeError`가 나지 않는지 확인한다.
- Solar/vLLM answer generation도 `Top-K`를 OpenAI 호환 요청 본문에 제대로 넣는지 확인한다.
- Triton sampling parameter에는 override가 있을 때만 `top_k`가 들어가는지 확인한다.
- 잘못된 override 값은 provider 호출 전에 바로 막히는지 확인한다.

## 2. 정제 회귀(Sanitization)
- planner filters에 `1번째`, `그`, `이번` 같은 말이 섞여 있으면 제거되고 `PLANNER.FILTER.ORDINAL_STRIPPED`가 남는지 확인한다.

## 3. 개수 계약 회귀(Count)
- `반도체 분야 과제 3건을 알려줘`처럼 개수를 분명히 말한 질문에서 planner가 `display_limit=3`을 내리면, 최종으로 보여주는 개수도 3건인지 확인한다.
- planner가 잘못된 개수를 내도 fallback 뒤 값이 `MAX_TOP_K_SIZE`를 넘지 않는지 확인한다.
- detail count 질문은 fallback이 동작해도 `limit=1`, `display_limit=1`을 유지하는지 확인한다.

## 4. 표시 스냅샷 회귀(Display Snapshot)
- list 응답 뒤 `view_state.latest_display_snapshot`이 저장되는지 확인한다.
- raw retrieval count와 visible count가 따로 기록되고, `RAG.COUNT_PIPELINE` / `RAG.COUNT_PIPELINE.RESULT`에 planner limit, runtime top-k, visible count가 함께 남는지 확인한다.
- `documents=10`, `canonical_evidence=1`, `requested_count=3` 같은 경우 보여주는 개수가 1로 줄지 않고 3으로 유지되는지 확인한다.
- `docs_count=1`, `canonical_count=10`, `requested_count=3`, `output_type=list` 같은 경우 canonical item evidence를 이용해 3개 항목 snapshot으로 복구되는지 확인한다.
- `docs_count=1`, `canonical_count=10`, `requested_count=20`, `explicit_count=3`, `output_type=list` 같은 경우에도 사용자가 말한 개수를 기준으로 복구되는지 확인한다.
- `DISPLAY.SNAPSHOT.BUILT`와 `RAG.COUNT_PIPELINE.RESULT`가 snapshot을 만들기 전의 `docs_count`, `canonical_count`, `visible_count`를 함께 남기는지 확인한다.
- 위 로그가 `docs_kind`, `canonical_kind`, `display_source`, `requested_count_source`도 함께 남기는지 확인한다.
- 개수 축이 맞지 않는 상황에서도 `RAG.CANONICAL_EVIDENCE.DERIVED` 또는 `RAG.DISPLAY_INPUT_MISMATCH`가 기록되는지 확인한다.
- 바깥 포장형 목록 흐름에서는 canonical item evidence가 충분할 때 `RAG.DISPLAY_INPUT_MISMATCH`보다 `RAG.DISPLAY_CANONICAL_AXIS.PROMOTED`를 우선 사용하는지 확인한다.
- planner retrieval query가 원래 질문 뜻을 바꾸면 `RAG.RETRIEVAL_QUERY.RESOLUTION`에 `drift_detected`, `drift_reasons`, `fallback_applied`가 기록되는지 확인한다.
- 해석된 후속 질문 anchor가 있는 detail lookup에서 planner query가 너무 일반적으로 바뀌면, `selected_search_query`가 anchor를 살린 compact query로 복구되고 관련 로그가 남는지 확인한다.
- `3rd project detail` 같은 resolved project ordinal follow-up에서는 planner drift가 성과 축을 추가하지 않고, 복구된 lookup query가 원래의 project anchor를 유지하는지 확인한다.
- perf 목록에서 고른 후속 질문에서는 planner merge가 `project`를 시도하더라도 `planner_service.apply_planner_strategy()`가 `base_route=perf`, `target_cols=[\"ntis_perf_v1\"]`를 최종값으로 강제하고 `FOLLOWUP.CONTEXT.RESTORED`에 attempted 값과 enforced 값을 함께 남기는지 확인한다.
- anchored detail follow-up에서 너무 일반적인 검색 질의가 나오면 anchor-locked exact lookup(`top_k=1`)으로 복구되는지 확인한다.
- 오래된 `latest_focus_entity`만 남아 있을 때는 anchor-locked exact lookup(`top_k=1`)이나 detail cache 적중을 억지로 타지 않는지 확인한다.
