# 운영과 환경

이 문서는 ADR-0018 권한분리 3계층 파이프라인 기준의 환경 변수, 부팅 방식, 운영 triage 순서, 검증 명령을 정리한다.

> **2026-05-18 갱신**: 레거시 `planner_stagewise`/`ExecutionManager`/`metrics` 엔드포인트 등이 모두 폐기되어 운영 표면이 크게 단순화되었다. 이전 문서의 OPS 이벤트 카탈로그는 더 이상 유효하지 않다.

## 주요 환경 변수

| 변수 | 설명 | 기본값 |
|------|------|--------|
| `REDIS_URL` | Redis 연결 URL | `apps.platform.settings.REDIS_URL` |
| `FILE_KVSTORE_ROOT` | File KV fallback 루트 | `local_kvstore` |
| `PIPELINE_SESSION_TTL_SECONDS` | KV에 저장되는 SessionMemory TTL(초) | `604800` (7일) |
| `METRICS_TIMEOUT_SECONDS` | 메트릭용 HTTP 클라이언트 timeout | `5` |

| `NTIS_LOCAL_MODELS_ROOT` | 로컬 모델 자산 루트 | repo의 `Models/` |

폐기된 환경 변수:
- `ENABLE_DEBUG_ROUTES` — `/query/debug` 폐기와 함께 제거
- `RAG_EVIDENCE_TOKEN_BUDGET`, `RAG_MIN_DENSE_SCORE`, `RAG_TOPK_DENSE`, `RAG_W_LEX`, `RAG_TOPK_LEX_CAND`, `RAG_OVERFLOW_QUEUE_SIZE`, `RAG_CONTEXT_COMPRESS_MAX_DOCS` — SearchAgent가 고정 strategy로 동작

- `LLM_DISAMBIGUATION_LABEL_ENABLED`, `LLM_PROSE_ENABLED`, `TURN_INTERPRETATION_LLM_FIRST` — 관련 모듈(`clarification_labeler`, `clarification_prose`, `turn_interpreter`) 폐기
- `AGENTIC_MAX_STEPS`, `AGENTIC_DECISION_REPAIR_MAX_ATTEMPTS` — Agent loop 자체가 단순화됨

## 운영 triage 순서

ADR-0018 적용 후 로그 신호가 단순화되어 다음 순서로 본다.

| 단계 | 로그 이벤트 | 확인 포인트 |
|------|-------------|-------------|
| 1 | `Redis connected` 또는 `File KV backend ready` | 부팅 시 KV 백엔드 결정 |
| 2 | `3-layer pipeline compiled successfully` | LangGraph 컴파일 성공 |
| 3 | `[load_session]` | conversation_id, session 복원 결과(`current_context.subject_name`) |
| 4 | `[node_judgment]` | `kind=search|direct_answer|clarification`, `strategy`, `latency_ms` |
| 5 | `[SearchAgent]` 또는 `[hybrid_search]`/`[exact_lookup]` | Qdrant 호출 자체 성패, 컬렉션·축 정보 |
| 6 | `[node_search]` | `status=single|multiple|empty|error`, `total_hits`, `latency_ms` |
| 7 | `[node_refine_judgment]`(있을 때) | multiple → refine 시도 결과 |
| 8 | `[FinalGuard]` | `unsupported_identifiers` 목록 (groundedness 위반 시) |
| 9 | `[node_final_guard]` | `decision=publish|clarify|internal_error`, `reasoning` |
| 10 | `[stream_metrics]` (LLMGenerator → openai_compat_llm) | TTFT, content_char_n, truncated |
| 11 | `[save_session]` 또는 `[session_store]` | SubjectQueryContext commit 여부 |

폐기된 OPS 이벤트:
- `REQ.START`, `REQ.SUMMARY`, `REQ.END`, `REQ.CONTEXT` — 라우트가 슬림 버전이라 발행 안 함
- `AGENT.STATE_CARD.BUILT`, `AGENT.DECISION`, `AGENT.TOOL_CALL`, `AGENT.TOOL_DIRECT_COMPILE`, `AGENT.REFINE_CURRENT_SUBJECT`, `AGENT.CLARIFICATION.*`, `AGENT.SUBJECT_CONTEXT.*`, `AGENT.LOOP_GUARD.TRIGGERED`, `AGENT.INTERNAL_ERROR` — 모두 폐기 (대체: `[node_judgment]`, `[FinalGuard]`)
- `PLANNER.STAGE*`, `PLANNER.PIPELINE`, `PLANNER.COUNT_CONTRACT`, `PLANNER.ASSEMBLE` — Planner 자체 폐기
- `RAG.EXECUTION_MANAGER.RESULT`, `RAG.RETRIEVE`, `RAG.RESULT.TOP`, `RAG.CONTEXT`, `RAG.DISPLAY_*`, `RAG.COUNT_PIPELINE*` — ExecutionManager 폐기
- `LLM.RESULT`, `LLM.GENERATE`, `ANSWER.STATE_DIAG` — merge_answers 폐기
- `STREAM.DONE`, `MEMORY.SNAPSHOT`, `FOLLOWUP.FACT_MISS`, `DETAIL.CACHE.MISS`, `REFERENCE.COLLECT`, `REFERENCE.FINALIZATION`, `REFERENCE.INVALID_PAYLOAD`, `SCOPE.TRANSITION`, `DISPLAY.SNAPSHOT.*`, `FOCUS.ENTITY.SET`, `CODE.FINGERPRINT`, `APP.CONFIG`, `REQ.ORACLE.DEFAULTS` — 모두 폐기 또는 슬림화

## 자주 발생하는 운영 이슈

### Redis 연결 실패

증상: 부팅 시 `Redis connection failed` 후 `File KV backend ready: <abs path>`.

원인: Redis 서버 다운 또는 네트워크 설정. 운영 환경에서 정상화 후 재부팅하면 Redis로 자동 복귀.

영향: 세션은 파일 KV에 저장되며 SessionMemory는 손실 없음. 다만 멀티 인스턴스 환경에서는 세션 공유가 안 됨.

### Qdrant 검색 실패

증상: `[hybrid_search] query_points failed: collection=... err=...` 또는 `[exact_lookup] qdrant scroll failed`.

진단:
1. Qdrant 클라이언트 자체가 살아있는지 확인 (`/health` 응답의 `graph_compiled=true`이면 부팅은 성공)
2. 컬렉션(`ntis_project_v1`, `ntis_perf_v1`) 존재 여부
3. payload index 누락 — exact_lookup이 사용하는 필드(`pjt_id`, `pjt_no`, `rst_id`, `person_no`, `org_id`, `prtcp_mp.hm_id` 등)에 keyword index가 있는지

조치: Qdrant 운영팀에 인덱스/컬렉션 점검 요청. 임시로 SearchResult.status=error로 흘러 사용자에게 internal_error로 노출됨.

### LLM 호출 timeout / 빈 응답

증상: JudgmentAgent의 `_llm_decide` 가 빈 JSON 반환 → clarification fallback. 또는 LLMGenerator의 `astream`이 빈 답변.

진단:
1. Solar/Gemma 서버 상태 확인 (vLLM, Triton 각각)
2. 입력 token 길이 (evidence block이 너무 크지 않은지)

조치: 일시적이면 사용자 재시도. 지속되면 LLM 서버 점검.

### `unsupported_identifiers` 다발

증상: `[FinalGuard] groundedness_issues=[...]` 로그가 빈번. clarification으로 닫힘.

원인: LLM이 evidence에 없는 식별자를 환각해 인용. 일반적으로 prompt 컨텍스트가 너무 커서 LLM이 다른 사실을 끌어들임.

조치: SearchTask.limit/display_limit이 적절한지(보통 10 이하), evidence block의 식별자 표기가 정확한지(`canonical_normalizer.py`의 `ids` 추출) 확인.

### session payload 손상

증상: `[session_store] schema mismatch` 또는 `invalid json` 로그. 사용자가 이전 대화 컨텍스트를 잃음.

원인: SessionMemory 모델 변경 후 기존 키 호환 실패. 또는 KV 외부 도구가 키를 수정.

조치: 해당 `conversation_id`의 `pipeline:v1:*:session` 키 삭제 후 재시작. SessionMemory는 이번 turn부터 새로 구성됨.

## 보안/프라이버시

- raw payload는 prompt에 직접 들어가지 않는다 (CanonicalEvidence 경유)
- LLM 응답 본문은 로그에 남지만(`apps/platform/openai_compat_llm.py` non-stream content), 운영 환경에서는 로그 레벨 조정 권장
- 사용자 입력 question은 로그에 남는다(`[node_judgment]`의 latency 로그). PII 정책에 따라 마스킹 필요 시 라우트 레벨에서 처리
