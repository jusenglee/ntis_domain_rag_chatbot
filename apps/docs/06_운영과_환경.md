# 운영과 환경

이 문서는 현재 저장소에서 실제로 참고해야 하는 환경 변수, 부팅 방식, 운영 triage 순서, 실행 가능한 검증 명령을 정리한다.

## Source of Truth

- 운영 surface: `apps/api/app_factory.py`, `apps/api/runtime.py`, `apps/api/routes.py`
- 설정 owner: `apps/platform/settings.py`, `apps/planner/planner_defaults.py`
- 함께 읽을 문서: `07_회귀기준과_점검.md`, `05_API_응답명세.md`

## 운영 요약

| 항목 | 현재 기준 |
|---|---|
| 앱 조립 | `create_app()` |
| KV backend | Redis 우선, 실패 시 File KV fallback |
| 문서 기준 루트 | `apps/docs` |
| planner prompt asset | `apps/prompts/*` 절대경로 기준 |
| follow-up context truth | `SessionMemory.current_context`; 여기서 복원한 projection은 view-state-equivalent context로 취급 |
| debug route | `ENABLE_DEBUG_ROUTES=true`일 때만 `/query/debug` 활성 |
| 기본 pytest 실행 전제 | repo 루트 + `PYTHONPATH=.` |
| Shock Absorber triage | `PLANNER.COUNT_CONTRACT` -> detail guard -> display snapshot -> publication guard 순서로 확인 |

### Planner 상세 로깅

Planner 장애는 같은 `request_id`에서 아래 순서로 확인한다.

- `PLANNER.STAGE1.START`, `PLANNER.STAGE15.START`, `PLANNER.STAGE2.START`: `prompt_version`, `question_preview`, `input_payload_fields`, `reasoning_effort`, `include_reasoning`, `disable_thinking`, `max_tokens`를 확인한다.
- `PLANNER.STAGE*.LLM_RESULT`: `raw_content_chars=0` 또는 `empty_content=1`이면 provider가 빈 content를 반환한 경로다. 이때 `json_candidate_count`가 0이면 JSON 파싱 이전 문제로 본다.
- `PLANNER.STAGE*.ERROR`: `error_phase`가 `llm_invoke`, `json_extract`, `parse`, `normalize`, `sanitize` 중 어디인지 확인한다.
- `apps.platform.openai_compat_llm` non-stream summary: `planner_stage`, `planner_prompt_version`, `choice_count`, `finish_reason`, `include_reasoning`, `reasoning_effort`, `disable_thinking`을 같이 확인한다.

전체 prompt와 raw retrieval payload는 로그에 남기지 않는다. 입력 payload는 필드별 문자 수와 짧은 질문 preview만 남긴다.

## Agentic front-controller logging

Agentic 전환 여부는 로그 순서와 agent 이벤트 필드로 판별한다.

- `agentic front-controller`: `LOAD.MEMORY` 이후 `rule_precheck`가 통과하면 `AGENT.STATE_CARD.BUILT(front_controller=true)`와 `AGENT.DECISION`이 먼저 찍혀야 한다.
- `TURN.TRIGGER`, `TURN.INTERPRETATION`, `TURN.POLICY_DECISION`이 `AGENT.DECISION`보다 먼저 찍히면 front-controller 전환 실패로 본다.
- ``이고 `agentic front-controller`이면 old front-controller shadow branch는 존재하지 않는다.

Agentic 필수 이벤트:

```text
AGENT.STATE_CARD.BUILT
AGENT.DECISION
AGENT.PARSE_ERROR
AGENT.SELF_REPAIR.START
AGENT.SELF_REPAIR.SUCCESS
AGENT.SELF_REPAIR.FAILED
AGENT.INVOKE_ERROR
AGENT.TOOL_CALL
AGENT.TOOL_DIRECT_COMPILE
AGENT.REFINE_CURRENT_SUBJECT
AGENT.CLARIFICATION.RECOVERY
AGENT.SUBJECT_CONTEXT.RETAINED
AGENT.SUBJECT_CONTEXT.SKIPPED
AGENT.TOOL_OBSERVATION
AGENT.TOOL_RETRY.START
AGENT.TOOL_RETRY.DECISION
AGENT.CLARIFICATION
AGENT.CLARIFICATION.BLOCKED
AGENT.CONTRACT_BLOCKED
AGENT.INTERNAL_ERROR
AGENT.LOOP_GUARD.TRIGGERED
```

Tool backend의 `planner_error`, `LLMJSONExtractionError`, `PLANNER.STAGE*.ERROR`는 사용자 모호성이 아니다. 정상 순서는 `AGENT.TOOL_OBSERVATION(observation_type=error)` -> `AGENT.TOOL_RETRY.START` -> `AGENT.TOOL_RETRY.DECISION`이며, 재시도 후에도 guarded intent가 없으면 `AGENT.INTERNAL_ERROR`로 닫혀야 한다. `AGENT.CLARIFICATION`은 Agent decision이 `ask_clarification`일 때만 허용된다.

운영 triage에서 특히 확인할 필드는 `current_context_type`, `staged_current_context_type`, `subject_kind`, `subject_name`, `publication_status`, `subject_publication_status`, `subject_continuity_retained`, `answer_publishability`, `tool_name`, `tool_execution_source`, `withheld_but_subject_retained`, `planner_llm_skipped`, `year_from`, `year_to`, `role`, `error_type`, `validation_errors`, `contract_block_reason`, `retry_count`, `retry_reason`이다. `AGENT.PARSE_ERROR`의 `raw_output`은 최대 2000자만 남기며, full prompt와 full state card는 로그에 남기지 않는다.

## Detail / follow-up 장애 triage

`logs/이슈 1.md` 유형의 장애는 아래 순서로 본다.

1. `AGENT.DECISION`에서 tool이 신규 검색인지 current-context refinement인지 확인한다.
   - 현재 화면 항목 상세인데 `search_ntis_domain`이면 routing 누수다.
   - `refine_current_subject` 또는 detail lookup 경로가 기대된다.
2. `AGENT.TOOL_CALL` / planner question preview에서 `1 items`, `people 10 items` 같은 parser-incompatible token이 들어갔는지 확인한다.
   - count는 자연어 suffix보다 구조화 `limit` / `display_limit` 메타로 전달하는 것을 우선한다.
   - subject activity 또는 current-subject refinement direct compile이면 `AGENT.TOOL_DIRECT_COMPILE`과 `planner_llm_skipped=1`이 남아야 한다. 첫 답변이 보류됐지만 subject continuity를 유지했다면 `AGENT.TOOL_OBSERVATION(staged_current_context_type=subject_query)` 이후 `AGENT.SUBJECT_CONTEXT.RETAINED(withheld_but_subject_retained=1, subject_continuity_retained=1)`도 확인한다.
3. `PLANNER.COUNT_CONTRACT`에서 `action=detail` 또는 `output_type=detail`인데 `limit/display_limit`이 `1/1`로 normalize됐는지 확인한다.
4. `RAG.EXECUTION_MANAGER.RESULT`에서 detail-like 요청이 `SEARCH_RECOVERY` 또는 `project_search` broad list로 내려갔는지 확인한다.
   - 단일 후보가 없으면 broad search가 아니라 clarification/internal observation으로 닫혀야 한다.
5. `DISPLAY.SNAPSHOT.BUILT`에서 `snapshot_first_title`, `display_first_title`, `canonical_first_title`이 서로 다른 축으로 벌어졌는지 확인한다.
6. `LLM.RESULT`와 `ANSWER.STATE_DIAG`에서 `blocked_state_consistency`, `unsupported_count`, `both_models_state_inconsistent`가 발생했는지 확인한다.
7. `STREAM.DONE`에서 Solar `TTFT_DEADLINE_EXCEEDED`가 있으면 provider/content 문제로 분리한다. 이는 routing/contract 원인의 결과를 악화시킬 수 있지만, detail broad search의 1차 원인은 아니다.
8. `reference.set`가 비거나 `Skipping invalid reference payload during stream finalization` warning만 남으면 `REFERENCE.INVALID_PAYLOAD`에서 `candidate_source`, `invalid_reason`, `top_level_pjt_id`, `top_level_rst_id`, `top_level_title1`, `top_level_title2`, `top_level_title_text`, `keys`를 먼저 본다.
   - `candidate_source=canonical_evidence`인데 `missing_tag`면 route의 canonical bridge에서 `source_type` 보존/매핑 또는 `pjt_id -> project` 보정이 빠졌는지 확인한다.
9. 같은 요청의 `REFERENCE.FINALIZATION`에서 `artifact_candidate_count`, `canonical_candidate_count`, `documents_used_candidate_count`, `invalid_candidate_count`, `emitted_reference_count`, `fallback_used`를 같이 확인한다.

Redis connection failed 후 File KV fallback, Oracle defaults unavailable/oracledb import failed는 개발환경 정상 동작으로 triage 우선순위에서 제외한다.
