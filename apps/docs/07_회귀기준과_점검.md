## 반드시 지킬 계약

| 계약 | 세부 규칙 |
|---|---|
| SEARCH | recall 우선, 사람/기관 hard must를 임의 추가하지 않는다 |
| LOOKUP / JOIN | precision 우선, server-side gate 유지 |
| Agent/Planner 위계 | Dialogue Agent가 정한 `Action`, `Subject`, `Axes`를 Planner가 기각하지 않는다. Planner는 이를 달성하기 위한 `mode`, `relation`, `filters`를 생성한다 |
| follow-up truth | source reference, ordinal, child anchor, recent mention, visible manifest truth를 섞지 않는다 |
| identifier semantics | `pjt_id`, `pjt_no`, `rst_id`를 같은 축처럼 다루지 않는다 |
| evidence boundary | raw payload 전체나 retrieval metadata 전체를 prompt에 직접 넣지 않는다 |
| degraded behavior | strict failure를 숨기려고 fallback chat이나 mode rewrite를 하지 않는다 |
| agentic dialogue | 신규 Dialogue Agent decision에는 이전 front-controller 경로을 두지 않는다. LLM parse/schema/tool validation 실패는 1회 self-repair 후 실패 시 `agent_internal_error`로 닫고, 사용자 모호성 clarification으로 변환하지 않는다. Tool backend planner 오류는 Agent에 1회 observation retry 후에도 실패하면 `agent_internal_error`로 닫는다. `search_subject_activity`와 `refine_current_subject` direct compile은 stagewise planner LLM을 호출하지 않는다. declared-but-unimplemented tool은 executor contract violation으로 닫는다 |
| detail routing | detail-like 요청은 broad `SEARCH_RECOVERY` list로 확장하지 않는다. 단일 대상이 없으면 Fail-closed 처리한다 |
| clarification boundary | 실제 사용자 대상 모호성에만 clarification을 사용한다. tool/planner/provider 오류는 clarification으로 위장하지 않는다 |

## 회귀 시나리오 체크리스트

### Route / reference

- invalid reference payload가 route 전체를 깨뜨리지 않고 fail-open으로 드롭되는지
- `/query/stream`이 `reference.set`과 `done`을 정상/오류/강등 종료 모두에서 유지하는지

### Follow-up / scope

- child detail follow-up에서 active scope truth가 유지되는지
- source reference나 ordinal follow-up이 planner 전략을 덮어쓰지 않는지
- `visible_answer_manifest`가 실제로 사용자에게 보인 목록의 truth만 소유하는지
- ADR-0014 follow-up gate가 `SessionMemory.current_context`를 공식 truth로 사용하고, projection은 view-state-equivalent context로만 쓰이는지
- ADR-0001 Dialogue Agent state card가 `SessionMemory.current_context`를 읽고, current-subject refinement tool call을 guarded `IntentPayloadV3` / `QuestionAnalysisV3`로 변환해 기존 retrieval path에 합류시키는지
- `SubjectQueryContext.publication_status=answer_withheld_subject_retained`일 때도 current subject refinement 권리가 유지되는지
- subject activity/refinement tool이 `next_current_context`를 staging하고, `merge_answers()`가 withheld answer + retrieval evidence 조건에서 이를 `answer_withheld_subject_retained`로 커밋하는지
- 동명 subject first turn이 복수 `person_no`를 관측하면 `SubjectQueryContext.identity_status=ambiguous_name_only`와 복수 candidate ID를 retain하는지
- `한국과학기술정보연구원 신동구` 같은 disambiguation follow-up이 단일 candidate로 수렴하면 `identity_status=resolved_with_org`로 승격되는지
- `planner_error` / `agent_internal_error` 같은 내부 오류에서는 ambiguity context를 새로 저장하지 않는지
- 동명 clarification 후보 라벨이 raw payload 없이 `disambiguator`/`aux`로 구분되는지

### Retrieval / contract

- lookup/join hybrid runtime failure가 `INTERNAL_ERROR` 대신 strategy violation/degraded answer로 표면화되는지
- `pjt_id`와 `pjt_no`가 join/detail 흐름에서 섞이지 않는지
- `action=detail` 또는 `output_type=detail`에서 `limit/display_limit=1/1` normalize가 적용되는지
- `1 items`, `people 10 items` 같은 parser-incompatible count token이 tool query materialization에 남지 않는지
- `신동구 연구자의 활동기록` 같은 people activity 질의가 `search_subject_activity`, `AGENT.TOOL_DIRECT_COMPILE`, `mode=LOOKUP`, `head=people`, `planner_llm_skipped=1`로 가는지
- `해당 연구자의 2014년~2023년 활동내역은?` 같은 refinement가 `refine_current_subject` direct compile로 가고 `search_ntis_domain`/stagewise planner로 재진입하지 않는지
- 단일 `pjt_id`가 확정된 project detail이 `LOOKUP_MISSING_RECOVERY` primary detail lookup으로 실행되는지
- 단일 후보 없는 detail이 `SEARCH_RECOVERY` 17건/20건 list로 확장되지 않는지

### 운영 환경

- Redis 실패 시 File KV fallback이 정상 동작하는지
- local model path와 metrics snapshot이 import/runtime smoke를 통과하는지

## 로그 점검 포인트

### Planner

```text
PLANNER.SIGNALS
PLANNER.STAGE1.START
PLANNER.STAGE1.LLM_RESULT
PLANNER.STAGE1
PLANNER.STAGE15.START
PLANNER.STAGE15.LLM_RESULT
PLANNER.STAGE15
PLANNER.STAGE2.START
PLANNER.STAGE2.LLM_RESULT
PLANNER.STAGE2
PLANNER.STAGE*.ERROR
PLANNER.ASSEMBLE
```

Planner 회귀 확인 시 `START -> LLM_RESULT -> STAGE 성공 이벤트` 순서가 같은 `request_id`로 이어져야 한다. 실패 케이스는 `PLANNER.STAGE*.ERROR.error_phase`로 `llm_invoke`, `json_extract`, `parse`, `normalize`, `sanitize` 중 어느 단계인지 식별 가능해야 한다. 빈 LLM 응답은 `LLM_RESULT.empty_content=1`, `raw_content_chars=0`, OpenAI compat summary의 `finish_reason` 조합으로 판단한다.

### Retrieval / evidence

```text
RAG.RETRIEVAL_QUERY.RESOLUTION
RAG.RESULT
RAG.CONTEXT
```

### Answer / 종료

```text
LLM.RESULT
REQ.SUMMARY
AGENT.DECISION
AGENT.PARSE_ERROR
AGENT.SELF_REPAIR.START/SUCCESS/FAILED
AGENT.INVOKE_ERROR
AGENT.TOOL_CALL
AGENT.TOOL_DIRECT_COMPILE
AGENT.REFINE_CURRENT_SUBJECT
AGENT.CLARIFICATION.RECOVERY
AGENT.SUBJECT_CONTEXT.RETAINED
AGENT.SUBJECT_CONTEXT.SKIPPED

AGENT.CLARIFICATION
AGENT.CLARIFICATION.BLOCKED
AGENT.CONTRACT_BLOCKED
AGENT.INTERNAL_ERROR
```

`AGENT.CLARIFICATION`은 Agent decision이 `ask_clarification`일 때만 허용된다. `planner_error`, `LLMJSONExtractionError`, `PLANNER.STAGE*.ERROR`는 사용자 모호성이 아니므로 `AGENT.TOOL_RETRY.*` 또는 `AGENT.INTERNAL_ERROR`로 이어져야 하며 `ClarificationContext`를 저장하면 안 된다.

## Agentic Dialogue golden gate

Agentic 전환의 핵심 acceptance criteria는 current subject follow-up이 clarification 없이 tool call로 이어지는지다.

필수 Golden Tests:

- G1: `신동구 연구자의 활동기록` 이후 `해당 연구자의 2014년~2023년까지의 활동내역은?`은 `AGENT.DECISION tool_name=refine_current_subject`, `year_from=2014`, `year_to=2023`이어야 한다.
- G2: `신동구 연구자의 2014년~2023년까지의 활동내역은?`은 subject와 기간을 보존하고 `search_subject_activity` 또는 current subject가 있으면 `refine_current_subject` direct compile로 가야 한다.
- G3: `연구책임자로 활동한 과제만 보여줘`는 current subject 기준 `refine_current_subject`, `role=연구책임자`, `target=project`여야 한다.
- G4: clarification 이후 짧은 `신동구` 응답은 새 검색어가 아니라 직전 unresolved constraints의 subject 보충으로 해석해야 한다.
- G5: current subject가 없고 동명이인 후보가 복수이면 `ask_user_for_clarification`이어야 한다.
- G6: `PJT_NO=S2296183 성과 전체`는 `pjt_no` group semantics를 유지하고 `pjt_id`를 임의 생성하지 않아야 한다.
- G7: `신동구 연구자(한국과학기술정보연구원)의 2014~2020년까지의 활동내역` 이후 `2020년에 진행한 프로젝트 상세정보 요청`은 현재 화면 후보를 기준으로 동작해야 하며, 특허/성과 list가 프로젝트 detail로 섞이면 실패다.
- G8: `과학기술지식인프라 융합서비스 개발 및 운영 (2020)` 또는 `[과학기술지식인프라 융합서비스 개발 및 운영 (2020)] 과제 상세정보`는 broad project search 17건으로 흐르면 실패다.
- G9: detail count가 parser mismatch로 `20`으로 오버라이드되면 실패다.
- G10: 단일 후보 미확정 상태에서 LLM 상세 답변 스트리밍이 시작되면 실패다.

실패 문구:

```text
무엇을 기준으로 좁힐지 먼저 목록이나 상세 대상을 정해 주세요.
질문을 조금 더 구체적으로 작성해 주세요.
대상을 다시 지정해 주세요.
```

위 문구가 current subject refinement 케이스에서 나오면 agentic UX 복구 실패로 본다.

추가 실패 상태:

```text
1 items
detail_count_contract_violation
SEARCH_RECOVERY on detail-like query
blocked_state_consistency after unrelated list expansion
```

위 상태가 `logs/이슈 1.md` 계열 시나리오에서 재발하면 Shock Absorber 회귀 실패로 본다.
