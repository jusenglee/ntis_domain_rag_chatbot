# 회귀기준과 점검

이 문서는 ADR-0018 권한분리 3계층 파이프라인이 지켜야 하는 계약과 repo 루트에서 실행 가능한 회귀 점검 명령을 정리한다.

> **2026-05-18 갱신**: 레거시 Golden Tests(G1~G11), Planner/ExecutionManager 회귀 로그 카탈로그는 모두 폐기되었다. 현재 회귀 안전망은 `tests/pipeline/` 의 65개 단위/통합 테스트로 대체되었다.

## 핵심 요약

| 항목 | 기준 |
|------|------|
| L1 의도 캐리어 | `SearchTask`로 평탄화 없이 전달 (frozen) |
| `pjt_id` / `pjt_no` | 혼용 금지 (ReferenceItem id 매핑도 분리) |
| canonical evidence 경계 | LLM prompt에 raw payload 직접 주입 금지 |
| ReferenceManifest | `published_rank` ↔ `source_snapshot_rank` 분리 (ADR-0017) |
| detail 액션 | `limit=1` 자동 normalize, multiple 시 refine 1회 |
| 에이전트 루프 | `refine_judgment` 최대 1회 (`refine_attempted` 플래그) |
| 검색기 책임 | SearchAgent는 SearchTask만 받고 의도 재해석 금지 |
| FinalGuard 책임 | 검색 재시도 없이 publish/clarify/internal_error 중 하나로 결정 |
| 최소 회귀 gate | `pytest tests/pipeline -q` + 부팅 smoke |

## 반드시 지킬 계약

| 계약 | 세부 규칙 |
|------|----------|
| **JudgmentAgent 책임** | 사용자 의도만 결정. Qdrant 호출, FinalGuard 결정 우회 금지 |
| **SearchAgent 책임** | SearchTask만 입력. drift detection / raw_query fallback 금지 |
| **FinalGuard 책임** | publish/clarify/internal_error 중 하나로 닫는다. 재검색 금지 |
| **SearchTask frozen** | 생성 후 수정 불가. refine은 새 SearchTask로 |
| **detail normalize** | `action=detail` → `limit=display_limit=1` 자동 적용 |
| **identifier semantics** | `pjt_id` / `pjt_no` / `rst_id` / `person_no` / `org_id`를 다른 의미로 다루지 않는다 |
| **ReferenceItem.id 매핑** | `IRD_NAI_PJT_INFO`→`pjt_id`, `IRD_NAI_RI_*`→`rst_id` (ADR-0017) |
| **evidence 경계** | raw Qdrant payload는 prompt에 직접 들어가지 않는다 |
| **refine 1회** | `refine_attempted=True`면 재진입 금지. 무한 루프 차단 |
| **clarify 비-commit** | FinalGuard.decision=clarify일 때 SubjectQueryContext commit 안 함 |
| **publish 시 commit** | search_task.subject가 있고 publish이면 SubjectQueryContext로 commit |
| **strategy 불변** | SearchAgent는 task.strategy를 실행 중 변경하지 않는다 |

## 회귀 시나리오 카탈로그

ADR-0018 §회귀 검증의 4건이 1차 회귀 시나리오다. 추가로 follow-up 6건이 보강되었다.

### S1 — 사람 + 기관 활동내역 (Rule-based)

입력: `신동구 연구자(한국과학기술정보연구원)의 활동내역을 알려줘`

기대:
- `JudgmentDecision.kind = "search"`
- `search_task.target = "people"`
- `search_task.subject.display_name = "신동구"`
- `search_task.subject.affiliation_org_name`에 `한국과학기술정보연구원` 포함
- `search_task.subject.identity_status = "resolved_with_org"`
- `search_task.strategy = "subject_anchor"`
- LLM 호출 없음 (rule-based pre-pass)

검증 테스트: `tests/pipeline/test_judgment_agent_rules.py::test_judgment_agent_person_org_skips_llm`

### S2 — 같은 세션 refine (Subject continuity)

입력 (S1 직후): `2020년 이후의 내역만 보여줘`

기대:
- `JudgmentDecision.kind = "search"`
- `search_task.subject.display_name = "신동구"` (직전 SubjectQueryContext에서 복원)
- `search_task.filters.year_from = 2020`
- `search_task.strategy = "subject_anchor"`
- LLM 호출 없음

검증 테스트:
- `tests/pipeline/test_judgment_agent_rules.py::test_judgment_agent_refine_year_with_subject`
- `tests/pipeline/test_workflow_followup.py::test_judgment_agent_uses_session_subject_for_refine`

### S3 — 코드형 식별자 detail (pjt_no)

입력: `K-20-L01-C07 의 상세정보 요청`

기대:
- `search_task.identifiers.pjt_no = ["K-20-L01-C07"]`
- `search_task.action = "detail"`
- `search_task.axis = "pjt_no"`
- `search_task.strategy = "exact_lookup"`
- `search_task.limit = 1`, `display_limit = 1`
- LLM 호출 없음

검증 테스트: `tests/pipeline/test_judgment_agent_rules.py::test_judgment_agent_pjt_no_code_skips_llm`

### S4 — 성과 식별자 detail (rst_id, EQU- 접두어)

입력: `6번 항목 - **검색엔진용 서버 (EQU-2020-01211283770)** 의 상세정보`

기대:
- `search_task.target = "perf"` (장비 접두어 EQU-)
- `search_task.identifiers.rst_id = ["EQU-2020-01211283770"]`
- `search_task.axis = "rst_id"`
- `search_task.strategy = "exact_lookup"`
- LLM 호출 없음

검증 테스트: `tests/pipeline/test_judgment_agent_rules.py::test_judgment_agent_rst_id_equ_target_is_perf`

### F1 — detail multiple → refine → single

`pjt_no` 검색으로 2건 → `refine_judgment` 1회 → `pjt_id`로 단일 후보 → publish.

검증 테스트: `tests/pipeline/test_workflow_followup.py::test_workflow_detail_multiple_refines_to_single`

### F2 — refine 1회 제한 → clarify

2건 → refine → 여전히 2건 → FinalGuard.decision=clarify.

검증 테스트: `tests/pipeline/test_workflow_followup.py::test_workflow_refine_once_then_clarify`

### F3 — clarify는 subject commit 안 함

JudgmentDecision.clarification → save_session에서 SubjectQueryContext 미생성 → SessionMemory.current_context는 EmptyContext 유지.

검증 테스트: `tests/pipeline/test_workflow_followup.py::test_workflow_clarify_does_not_commit_subject`

### F4 — publish 시 subject commit

publish + search_task.subject → SubjectQueryContext로 commit → 다음 turn에서 복원 가능.

검증 테스트: `tests/pipeline/test_workflow_followup.py::test_workflow_publish_commits_subject_query_context`

### F5 — direct_answer는 검색 우회

`JudgmentDecision.direct_answer` → Qdrant 호출 0회 → AnswerArtifact.answer_kind="direct_answer".

검증 테스트: `tests/pipeline/test_workflow_followup.py::test_workflow_direct_answer_bypasses_search`

### F6 — FinalGuard groundedness 위반 → clarify

답변이 evidence에 없는 식별자(예: 9999999999) 인용 → FinalGuard.decision=clarify, diagnostics.unsupported 보고.

검증 테스트: `tests/pipeline/test_final_guard.py::test_final_guard_unsupported_identifier_blocks`

## 로그 점검 포인트 (회귀 시 우선 확인)

| 회귀 의심 | 1차 로그 신호 |
|-----------|----------------|
| LLM 호출이 너무 많음 (Rule path 깨짐) | `[node_judgment]`의 `latency_ms`가 일관되게 1초 이상 |
| L1 의도 누수 (식별자 증발) | SearchTask 로그에서 subject/identifiers 비어 있는데 hybrid_search로 흐름 |
| Qdrant 필터 누락 | `[hybrid_search]` 또는 `[exact_lookup]` 후 0건이면서 `target=people`인데 person filter 없음 |
| refine 무한 시도 | `refine_attempted` 가 다음 turn까지 True로 남아 있음 |
| publish 시 subject 미커밋 | 다음 turn `[load_session]` 에서 직전 turn의 subject_name이 사라짐 |
| Groundedness 다발 실패 | `[FinalGuard] groundedness_issues=[...]` 가 빈번 |
| ReferenceManifest 누락 | `done.meta.references = []` 인데 답변 본문에 `[N]` 인용 있음 |

## 폐기된 회귀 카탈로그

다음은 ADR-0018 이전 회귀 안전망. 현재 시스템에서 더 이상 적용 불가.

- **Planner/ExecutionManager 로그 카탈로그** (`PLANNER.STAGE*`, `RAG.EXECUTION_MANAGER.RESULT`, `RAG.RETRIEVE` 등)
- **Golden Tests G1~G11** (`tests/golden/test_agentic_dialogue_shindonggu.py` 등)
- **Agentic Dialogue golden gate** — `search_subject_activity` / `refine_current_subject` 도구 자체가 폐기됨
- **detail count contract violation** — SearchTask 모델 검증으로 동일 기능 보장
- **SEARCH_RECOVERY broad search 누수** — strategy 자체가 enum 화이트리스트로 봉인됨
- **`blocked_state_consistency`** — `answer_state_consistency` 모듈 자체가 폐기됨
- **`Smart Coercion` 회귀** — 단일 SearchTask 빌더로 흡수됨

이 항목들은 같은 회귀가 새 시스템에서 재현될 수 있다면 `tests/pipeline/` 에 재작성하면 된다.
재작성하지 않으면 동일 회귀 안전망이 없는 상태로 간주.
