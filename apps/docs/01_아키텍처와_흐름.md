# 아키텍처와 흐름

이 문서는 NTIS Domain RAG를 **retrieval-first 검색 시스템 + chat UX** 관점으로 설명합니다.
핵심은 "어떻게 찾을지 먼저 정하고, 그 근거를 만든 뒤, 마지막에야 답을 표현한다"는 계층 분리입니다.

## 한 줄 요약
- 이 시스템은 planner, retrieval, 근거 조립, 채팅 UX를 분리해 검색 정확도와 설명 품질을 함께 지키려는 구조다.

## 이 문서를 읽을 사람
- 시스템 전체 흐름을 잡아야 하는 신규 개발자, PM, 운영자

## 이 문서에서 바로 찾을 수 있는 것
- 왜 계층을 나눴는지
- 요청 1건이 지나가는 큰 흐름
- 핵심 artifact와 소유권
- 계층별 금지 사항

## 지금 챙길 것
- planner는 "무엇을 찾을지", retrieval은 "실제로 찾는 일", answer generation은 "근거를 읽기 쉽게 설명하는 일"이라고 나눠 이해하면 된다.
- `contract`는 단계 사이에서 절대 흐리면 안 되는 약속, `canonical evidence`는 raw 결과를 정리한 근거, `drift`는 질문 뜻이 중간에 흐트러지는 현상이다.
- 이 문서는 시스템 설명용이고, 세부 규칙은 `02_실행계약과_전략규칙.md`, 운영 확인은 `03_운영과_환경.md`에서 본다.

핵심 원칙은 간단합니다.

- 먼저 올바른 retrieval 전략을 고정한다.
- 그 전략으로 근거를 수집하고 canonical evidence를 만든다.
- 그다음에야 답변 문장, 스트리밍, 대화 UX가 붙는다.

즉, 답변 표현은 중요하지만 retrieval contract를 바꾸는 계층이 아닙니다.

## 현재 코드 패키지 기준

- `apps.api`: route, runtime wiring, transport, manifest
- `apps.planner`: query intent, planner stage/runtime/service
- `apps.conversation`: follow-up, scope, anchor, session/view-state
- `apps.retrieval`: retrieval/filter/compile/orchestration/runtime
- `apps.evidence`: canonical evidence, detail/context/render, result assembly
- `apps.chat`: answer generation, llm runtime, streaming runner
- `apps.platform`: shared settings, schemas, storage, provider clients
- 레거시 호환 디렉터리는 삭제 완료 상태이며, 현재 구현은 위 feature package root만 사용한다.

## 1. 시스템을 4개 층으로 이해한다

### 1) 질의 이해 (Query Understanding)
입력:
- 사용자 질의
- conversation_hint (대화 힌트)
- 이전 canonical_evidence (정규화된 근거)

출력:
-  question_analysis (질의 분석)
-  intent_payload.normalized_intent (정규화된 의도 페이로드)

책임:
- 질의에서 검색 의도를 읽고, exact_id (정확한 식별자), candidate_key (후보 키) 등을 추출하여 **planner (플래너)**가 사용할 입력을 생성합니다.

금지:
- 최종 실행 전략을 여기서 멋대로 확정하지 않는다.
- raw payload(검색된 데이터)를 prompt에 바로 넣지 않는다.

### 2) Retrieval 실행
입력:
- 조립된 `strategy`(실행 전략)
- `compiled filter` (컴파일된 필터)
- `runtime policy` (실행 시점 정책)

출력:
- retrieval hit (검색 적중 결과)
- join hop result (조인 홉 결과)
- execution metadata (실행 메타데이터)

책임:
- SEARCH / LOOKUP / JOIN을 계약대로 수행한다.
- contract violation (계약 위반) 은 fail-close(오류 시 기본 차단)로 처리한다.
- 하위 레이어에서 새 전략을 만들지 않는다.

금지:
- `mode`, `relation`, `join_key_mode`, `target_cols`를 새로 만들지 않는다.
- invalid strategy를 조용히 다른 strategy로 바꾸지 않는다.

### 3) 근거 조립
입력:
- retrieval hit
- execution mode / route / output_type

출력:
- `canonical_evidence`
- `render_profile`
- context text

책임:
- raw retrieval payload를 canonical schema로 정규화한다.
- `output_type`에 맞는 evidence presentation shape를 고른다.
- `pjt_id`, `pjt_no`, 기관 역할 의미를 보존한다.

금지:
- retrieval metadata 전체를 LLM에 그대로 노출하지 않는다.
- retrieval view와 prompt view를 같은 artifact처럼 다루지 않는다.

### 4) 채팅 UX
입력:
- canonical evidence
- render profile
- answer policy
- conversation state

출력:
- 사용자 응답
- stream event
- conversation memory snapshot

책임:
- retrieval 결과를 읽기 쉬운 답변으로 변환한다.
- memory, follow-up, streaming을 관리한다.
- degraded response가 필요할 때 사용자 경험을 관리한다.

금지:
- retrieval contract를 바꾸지 않는다.
- canonical evidence 없이 임의 답변을 우선하지 않는다.

## 2. 요청 1건은 이 순서로 흐른다

1. **Request ingress**
   - API route가 workflow seed를 만든다.
   - 이 단계에서는 retrieval 전략을 결정하지 않는다.

2. **질의 이해 / intent assembly**
   - `question_analysis`
   - `intent_payload.normalized_intent`

3. **planner contract / strategy assembly**
   - deterministic gate와 planner merge를 거쳐 `strategy`를 조립한다.

4. **runtime prelude / strict validation**
   - `strategy`를 검증하고 `RuntimePreludeResult`를 만든다.

5. **retrieval execution**
   - SEARCH / LOOKUP / JOIN orchestration을 수행한다.

7. **evidence assembly**
   - retrieval result를 `canonical_evidence`와 `render_profile`로 바꾼다.

8. **answer generation / chat UX**
   - canonical evidence를 바탕으로 응답을 생성하고 stream을 관리한다.

9. **response / ops summary**
   - 최종 응답과 `REQ.SUMMARY`를 남긴다.

## 3. 핵심 artifact는 누가 책임지는가

### `question_analysis`
- planner artifact입니다.
- 실행 진실(execution truth)이 아닙니다.
- debug와 drift 진단에는 유용하지만, 하위 runtime이 그대로 truth처럼 쓰면 안 됩니다.

### `intent_payload.normalized_intent`
- retrieval가 소비하는 canonical 질의 객체입니다.
- query understanding의 최종 산출물이며 retrieval workflow의 기본 입력입니다.

### `strategy`
- 실행 전략의 진실입니다.
- planner merge에서 `base_route/target_cols` 최종값을 확정하고, contract validation, runtime prelude를 통과한 최종 실행 전략입니다.

### `canonical_evidence`
- retrieval 결과 정규화의 진실입니다.
- raw retrieval payload를 prompt에 직접 넣지 않고 canonical schema로 바꾼 결과입니다.

### `render_profile`
- 표현 계약입니다.
- `output_type`에 따라 어떤 evidence shape를 만들지 결정합니다.
- 답변 문체를 정하는 객체가 아닙니다.

## 5. 각 계층에서 하지 말아야 할 일

| 계층 | 할 수 있는 일 | 하면 안 되는 일 |
|---|---|---|
| 질의 이해 | retrieval intent 조립, hint 정규화 | final runtime strategy 재결정 |
| Retrieval 실행 | contract enforcement, compile, retrieval 수행 | 새 mode / relation / join key 발명 |
| 근거 조립 | canonicalization, render profile 선택 | source semantics 변경 |
| 채팅 UX | 응답 표현, streaming, 대화 흐름 | retrieval contract 변경 |
 
## 6. 운영에서는 무엇을 더 우선하는가

운영과 디버깅에서의 우선순위는 아래와 같습니다.

1. retrieval strategy correctness
2. join / filter correctness
3. canonical evidence fidelity
4. render / output correctness
5. chat UX correctness
# Scope-Aware Follow-up Flow
- 현재 follow-up 검색 흐름의 기준점은 `planner`가 아니라 planner 앞의 `request_facade` follow-up orchestrator다.
- 최신 runtime 흐름은 `Rule Precheck -> Hard Signal / Turn Interpreter / Turn Policy -> Scope Resolver(reset/refinement/clarification) -> Planner(SEARCH/LOOKUP/JOIN) -> Execution Constraint Compiler -> Retrieval -> Result Projection / Scope Update -> Memory Save` 순서를 따른다.
- `SEARCH/LOOKUP/JOIN`의 의미는 planner가 결정하고, pre-planner follow-up resolution은 hard signal과 candidate contract를 통해 “무엇을 가리키는가”만 고정한다.
- `ConversationViewState.active_scope`는 `result_set`, `focus`, `child_anchor`, `parent_chain`, `scope_kind`를 저장해 list/detail/child 전이를 함께 보존한다.
- child anchor는 현재 상세 내부의 하위 엔티티를 exact id로 다시 꺼내기 위한 runtime 객체다. people/org/perf child ref에서 usable id가 있는 경우에만 승격한다.
- execution constraint compile 단계는 resolved anchor를 `ids_map`으로 다시 고정한다. exact id seed가 있으면 broad name-only widening은 허용하지 않는다.
