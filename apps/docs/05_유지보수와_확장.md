# 유지보수와 확장

이 문서는 현재 구조 debt, 우선순위, 재발 방지 규칙을 정리한다.
새 기능보다 기존 계약과 텍스트 무결성을 먼저 지키는 것을 기본 원칙으로 둔다.

## 한 줄 요약
- 이 문서는 무엇을 먼저 고치고, 어떤 실수를 다시 만들지 말아야 하며, 문서를 언제 같이 갱신해야 하는지 정리한 유지보수 기준서다.

## 이 문서를 읽을 사람
- 개발자, 운영자, 문서 정비를 맡는 사람

## 이 문서에서 바로 찾을 수 있는 것
- 현재 우선순위
- 변경할 때 지켜야 할 원칙
- UTF-8 재발 방지 규칙
- 어떤 변경이 생기면 어떤 문서를 같이 고쳐야 하는지

## 지금 챙길 것
- 새 기능보다 contract drift, 문서 drift, UTF-8 손상 재발을 먼저 막아야 한다.
- 한글 파일은 최소 라인 패치 원칙을 지키고, 기능 변경과 인코딩 복구를 섞지 않는다.
- planner / runtime / streaming / baseline owner가 바뀌면 운영 문서와 회귀 문서를 같이 갱신한다.
- feature-sliced cutover는 hard cut까지 끝났고, 현재 구현은 `apps.planner`, `apps.conversation`, `apps.evidence`, `apps.retrieval`, `apps.chat`, `apps.platform` 아래에만 둔다.

## 현재 우선 리스크
- follow-up과 scope/anchor처럼 사용자 체감이 큰 흐름이 runtime upstream에서 다시 흔들릴 수 있다.
- 문서가 실제 source-of-truth보다 늦게 갱신되면 잘못된 운영 루프가 굳어진다.
- UTF-8 손상은 기능 버그와 별개로 문서 신뢰도를 한 번에 무너뜨린다.

## 지금 확인할 로그/테스트
- 문서 변경 뒤에는 UTF-8 explicit read와 `git diff`로 대량 churn이 없는지 먼저 본다.
- 기능 계약을 건드린 경우 `tests/test_planner_stagewise.py`, `tests/test_runtime_helpers_stream_bypass.py`, `tests/test_api_routes_reference_payload.py` 축을 우선 본다.

## 다음 문서 업데이트 트리거
- 계약 / planner / filter / streaming / baseline ownership / follow-up policy가 바뀌면 이 문서와 관련 코어 문서를 함께 갱신한다.

## 1. 지금 우선순위를 이렇게 본다

### P0. strict contract 유지

- planner / contract / runtime 사이에 silent correction이 다시 들어오지 않게 막는다.
- compat fallback이 기본 경로처럼 확장되지 않게 막는다.
- `pjt_id`와 `pjt_no` 의미가 섞이지 않도록 검증을 유지한다.

### P1. JOIN runtime observability 정리

- `join_compile_selection`
- `hop2_key_strategy`
- `resolved_runtime_key_kind`

위 필드의 vocabulary와 로그 해석 기준을 일관되게 유지한다.

### P1. 텍스트 무결성 / UTF-8 위생

- 문서와 핵심 코드에서 깨진 한글, mojibake, 의도치 않은 `?` 대체 문자를 남기지 않는다.
- 한글 포함 파일은 shell 기반 전체 재저장 방식으로 수정하지 않는다.
- 한글 파일 수정은 최소 라인 패치 원칙을 사용한다.
- 기능 변경과 인코딩 복구를 동시에 할 때는 diff가 검토 가능하도록 논리적으로 분리한다.
- UTF-8 무결성 검사는 follow-up이 아니라 변경 완료 조건으로 본다.

권장 추가 점검:
- 운영 문서와 계약 문서에 대한 텍스트 무결성 체크
- retrieval drift 관련 한국어 혼합 질의 회귀 테스트

### P2. retrieval robustness 확장

- broad topic 질의
- 비교 질의
- 복합 조건 질의
- follow-up 질의

위 유형은 retrieval policy, reformulation, ranking, evidence shaping 관점에서 보강한다.

## 2. 변경할 때는 이 원칙을 지킨다

- planner contract는 strict baseline으로 유지한다.
- `SEARCH / LOOKUP / JOIN` 경계를 흐리지 않는다.
- parser / planner / runtime이 서로 전략 의미를 임의 보정하지 않는다.
- raw payload를 prompt에 직접 넣지 않는다.
- canonical evidence를 거친 뒤 renderer에서 prompt view를 만든다.

## 3. UTF-8 사고를 다시 만들지 않으려면

### 금지 패턴

- PowerShell이나 shell에서 한글 포함 파일을 문자열 치환으로 통째로 덮어쓰기
- 콘솔에 보이는 텍스트를 그대로 source of truth처럼 복사해 다시 저장하기
- 인코딩 복구와 기능 변경을 구분하지 않고 한 번에 대량 수정하기

### 필수 절차

1. 수정 전 원문과 현재 diff를 분리해 인코딩 손상 범위를 확인한다.
2. 한글 파일은 최소 라인 패치만 적용한다.
3. 수정 후 UTF-8로 다시 읽어 깨진 문자가 없는지 확인한다.
4. git diff에서 의도치 않은 대량 churn이 없는지 확인한다.
5. 한글 토큰화나 한국어 질의 처리 경로를 건드렸다면 회귀 테스트를 추가한다.

## 5. 장기적으로는 이렇게 유지한다

- retrieval correctness를 answer style보다 우선한다.
- raw -> canonical -> prompt 흐름에서 의미 보존을 최우선으로 둔다.
- 문서와 스킬은 구현 가이드뿐 아니라 재발 방지 장치로 유지한다.

2026-04-02 기준 package ownership은 `docs/ADR/ADR-0013-feature-sliced-package-cutover.md`를 따른다.
